- **All 22 body-reading Real Mode routes use `readBoundedJsonBody()`** (`lib/real/server/http.ts`); the legacy `readJsonBody()` is gone and source guards keep it gone. Limits measure UTF-8 transport bytes: **4 KiB** control (14 routes), **16 KiB** WebAuthn assertion (4), **64 KiB** signed Turnkey (2), **64 KiB** WebAuthn registration (2). The two 64 KiB policies are separate constants. An over-limit body is HTTP 413 `{ error, code: "request_too_large" }`, before any challenge, claim, signing, budget charge or durable write.
- **Global ceiling: 10 MiB when 3B closed (`d9a0564`); 256 KiB (262 144 bytes) since the separate post-3B change below.** `REAL_API_MAX_BODY_BYTES` (`request-gate.ts`) equals `next.config.ts`'s `experimental.proxyClientMaxBodySize` and must stay equal (the parity test requires strict equality). The proxy gate requires `Content-Length` on body routes (missing → 411, malformed → 400, above the ceiling → 413) after the 403 and 415 checks; body-less routes and safe methods are exempt.
- **Not deployment-ready.** The reader is not an early network limit and does not stop slow uploads; Next.js still buffers and drains uploads. The 64 KiB registration limit rests mainly on offline synthetic models, not a real-device matrix (a false 413 could orphan a passkey). Hosting and CDN limits, timeouts, per-IP protection, HTTP/2 and HTTP/3 and Firefox testing, remaining registration admission and abuse controls (the Milestone 1 dispatch ceilings already exist), production provider-budget policy and migration, script CSP, a host-specific RP ID and origin, the platform duration limit, and the HSTS and host-only (`__Host-`) cookie decisions all remain to be done (the session cookie already uses HttpOnly, SameSite=Lax and Secure in production). The known "FIX 3" ordering flake and the Practice `Date.now()` race are still open; the 3B-4 audit's full run was 4880 passed / 1 failed (that known flake) / 322 skipped, not a clean pass.

## Post-3B Global Body Ceiling (256 KiB) — controlled development only, NOT deployable

A separate post-3B hardening change, not a reopening of Milestone 3B and not 3C/3D/3E; ARCHITECTURE.md's "Post-3B Global Body Ceiling" is the record. `REAL_API_MAX_BODY_BYTES` went from 10 MiB to `262_144` (256 KiB) for controlled local development; it is the single shared constant for the gate and Next.js's body-copy limit, so never add a second literal or loosen the strict-equality parity test. All 22 route-level limits are unchanged, as are the 403 / 415 / 411 / 400 / 413 gate contracts. The gate still runs before authentication, so an over-ceiling request gets 413 before any 401. The framework still buffers and drains oversized uploads, so slow-upload and connection exhaustion are unresolved; its over-limit console warning is cheaper to trigger (accepted localhost residual, no log-volume protection); real-device registration measurements remain incomplete. Changing the ceiling again needs a separate policy decision. The public-deployment prerequisites above are unchanged, and public deployment remains unauthorized.

## Hard Constraints

- **Practice Mode uses fake money only and stays unchanged.** Do not modify `simulation/**`, `lib/stores/simulation-store.ts`, Practice financial semantics, or the Practice persistence version for Real Mode work. Practice and Real are parallel paths (see ARCHITECTURE.md); real financial state never goes through the simulation engine.
- **Real Mode is testnet-only.** No mainnet, no real-value funds, no production custody, for the whole of Phase 2. Nothing in the app may hold private keys or seed phrases, and nothing may store them in Zustand or browser persistence.
- **Blockchain SDKs live only in `lib/real/**`** (and secret-holding route handlers under `app/api/real/**`). Components, pages, and stores use `lib/real`'s interface. ESLint enforces this; don't work around it.
- **The Real Mode feature flag (`NEXT_PUBLIC_REAL_MODE_ENABLED`) is authoritative.** The client enforces it in one place, `lib/stores/mode-store.ts` (build-time value). The server enforces it at runtime in `lib/real/server/config.ts` (every `app/api/real/**` route and the request gate). Don't add per-page or per-component flag checks.
- **External facts about SDKs, networks, and services are candidates until verified.** ARCHITECTURE.md marks them as such; don't document or code them as settled without checking current sources first.
- **Hide jargon, not concepts.** Plain-language explanations and consequences come first; terms like gas, slippage, liquidity, LTV, or liquidation threshold are introduced contextually once they help the user understand what just happened, not permanently hidden. The goal is for users to eventually understand these concepts by name — don't add developer/protocol-facing language to consumer-facing surfaces "for accuracy," but don't scrub the vocabulary out of the product either.
- **This is a single-developer project.** Do not introduce abstractions, frameworks, services, or dependencies to solve problems that don't exist yet. Prefer the smallest, most boring solution that works. See ARCHITECTURE.md's principles before adding structure.
- **Design decisions are intentionally deferred.** Do not invent or lock in a color palette, typeface, or component library on your own initiative. If DESIGN.md still lists something as "deliberately undecided," ask before treating it as decided, or propose an option explicitly rather than silently picking one.
- **Don't jump batches.** Build only the ROADMAP.md batch the user has authorized — no wallet, RPC, contract, or transaction code as "groundwork" for a later batch, even if it seems reasonable. Confirm with the user first.
