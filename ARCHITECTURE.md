# ARCHITECTURE.md

## Status

This document records the architectural **principles**, the **decisions actually made** so far (Phase 1, Phase 2, and the post-Phase-2 security closeout — Batch 2g, 2g-H, and slices S1–S5, ending in the S5 security freeze), and what is still open. Decisions are listed with brief rationale; anything in "Explicitly Not Yet Decided" or marked as a *candidate* should not be read as settled.

## Guiding Principles

- **Appropriate for one developer.** Every architectural choice should be justified by what a single person can build, understand, and maintain. No microservices, no distributed systems, no infrastructure that exists to support a team or scale we don't have.
- **Avoid premature abstraction.** Build the simplest thing that satisfies the current phase (see [ROADMAP.md](ROADMAP.md)). Don't build a plugin system, a generic "protocol adapter framework," or configurable everything before there are at least two real cases that need it.
- **Simulate first, generalize later.** The MVP's financial logic (balances, swaps, yield, borrowing, liquidation) should be implemented as a straightforward simulation — plain data and logic, not a blockchain client pretending to be one.
- **Practice and Real are parallel paths, not one engine with two backends.** The Practice simulation is pure and synchronous; real chain interaction is asynchronous with intermediate states. Forcing both behind one interface would make the simulation worse at its job without making Real Mode better at its own. They share the presentation layer (formatters, rows, notes, the shell) — never an engine, a store, or persisted state. See "Phase 2 Decisions".
- **Boring and legible over clever.** Prefer well-understood, widely-documented tools and patterns. A solo developer's biggest risk is complexity they can't hold in their head or debug alone.

## Conceptual Boundaries

- **Simulation / ledger layer** (`simulation/`) — owns the fake financial state: balances, positions, rates, collateral, and the rules for how actions (swap, deposit, borrow, repay) change that state, including liquidation logic. Pure, synchronous, framework-agnostic; it does not know how it's displayed and does not know Real Mode exists.
- **Real layer** (`lib/real/`, populated starting Phase 2 Batch 2a with the pure/signing layer; account provisioning/restoration (2b), balance reads (2c), Cash payment submission (2d), and a bounded payment-history read (2e) are built and live-verified, as is the post-Phase-2 security closeout — backup passkeys (2g/2g-H), payment attribution and reconciliation (S1/S2), operator removal recovery (S3), session hygiene (S4), and the S5 freeze) — owns everything about a real account and real chain interaction: account identity, balance reads, transaction submission and status. Asynchronous, framework-agnostic, and fenced from the simulation in both directions. It is the *only* place a blockchain SDK may be imported (plus server-side route handlers under `app/api/real/**` that must hold a secret).
- **Presentation layer** — the UI and interaction design described in [DESIGN.md](DESIGN.md). It reads from and issues actions to *either* the simulation store or the Real store, chosen per page by the mode boundary, and owns all the contextual education/teaching-moment logic. Components never import a chain SDK.

Originally this document anticipated a "chain adapter" that would satisfy the same shape of requests as the simulation layer. That was dropped when Phase 2 was actually scoped — see the principle above and "Phase 2 Decisions" below.

## Phase 1 Decisions

The following technical choices have been made for Phase 1 (see [ROADMAP.md](ROADMAP.md)). Each is chosen for being the smallest, most boring option that satisfies Phase 1 without foreclosing Phase 2.

- **Framework/language: Next.js (App Router) + React + TypeScript.** The deepest ecosystem for consumer-grade UI, and TypeScript catches bugs in financial state transitions at compile time. Next.js also provides routing and server-side capability (route handlers) in one project, with no separate backend service for a solo developer to run — which Phase 2 relies on for anything that must hold a secret.
- **Styling: Tailwind CSS.** Expresses spacing, type scale, and layout directly without committing to a themed design system, consistent with DESIGN.md still leaving exact visual identity undecided.
- **Component foundation: shadcn/ui.** Used as a source of accessible, unstyled primitives (dialogs, tooltips, popovers — needed for contextual education moments), not as a themed component library. Components are copied into the codebase and customized to match DESIGN.md rather than kept in their default visual identity. Only components actually needed are added — no bulk install of the full set. See the corresponding note in [DESIGN.md](DESIGN.md).
- **Application/simulation state: Zustand.** Portfolio, swap, earn, and borrow/liquidation all read and mutate the user's real Practice Mode financial state through one shared store, rather than component-local state that would need to be lifted and merged later. Explore is a deliberate exception — see "Explore sandbox" below.
- **Simulation engine: plain, framework-agnostic TypeScript.** Pure, deterministic functions (`applyAction(state, action) → newState`) with no dependency on React, Next.js, or any UI code. This is the "simulation/ledger layer" boundary described above — kept framework-agnostic so it's cheap to test, and kept unchanged by Phase 2 (Real Mode is a parallel path, not a second implementation of this interface).
- **Explore sandbox: isolated, ephemeral `SimulationState` — not the Zustand store.** Explore's interactive experiments (`lib/explore/experiment-state.ts`, `lib/explore/use-experiment-simulation.ts`) each get their own `SimulationState`, built by `createExperimentState()` from `createInitialState()` plus real `applyAction()` calls — never from a reference to the user's actual Practice portfolio. A `useExperimentSimulation()` hook holds that state in plain React state local to the experiment's component and dispatches into it via the same `applyAction()` the rest of the app uses, with a fixed simulated clock (`EXPERIMENT_NOW_MS`) so every fixture and every scenario is fully deterministic. This was chosen over (a) mutating the user's real Practice state directly, and (b) snapshotting and restoring it around an experiment: both make an experiment's "reset" ambiguous with the user's own portfolio, and (b) additionally breaks determinism (real dispatch reads the wall clock) and risks the persist middleware writing sandbox state to `localStorage` if an exit path is missed. An isolated sandbox reuses the same engine and financial math with no new abstraction, needs no persistence migration (experiment progress isn't the user's money and has no value across sessions), and can't reach the main store even by mistake — enforced by an ESLint rule banning `@/lib/stores/simulation-store` imports from `components/explore/**` and `lib/explore/**`, and proven by tests asserting the main store's state is referentially unchanged (`toBe`, not just `toEqual`) after driving every control in every experiment.
- **Persistence: browser storage (localStorage/IndexedDB).** Phase 1 is a single-user sandbox with fake money and no accounts, so there is no requirement yet for server-side or cross-device storage. Accessed through a small persistence module so a future backend swap touches one place, not the whole app.
- **Authentication: none in Phase 1.** There is nothing to protect — state lives in the user's own browser. Avoids building an accounts system now that would likely be redone once Phase 2/3 introduce real wallets and real funds.
- **Testing: Vitest for the simulation engine, React Testing Library for key interaction tests.** The simulation engine's purity makes it cheap to test thoroughly (swap math, collateral ratios, liquidation triggers), which matters most since bugs there would most directly undermine user trust. React Testing Library covers a small number of critical flows, not full coverage.
- **Charting: Recharts, installed only when a chart is actually needed.** Declarative and React-native; avoids solving rendering/interaction problems by hand that a library already solves.
- **Animation: Framer Motion, installed only when CSS/Tailwind transitions aren't enough.** Tailwind's transition utilities handle simple cases; Framer Motion is reserved for more expressive, stateful motion (e.g., the liquidation moment).
- **Deployment: Vercel.** Zero-config for Next.js, no infrastructure for a solo developer to manage.
- **Package manager: pnpm.** Fast, disk-efficient, and catches phantom-dependency bugs via its strict dependency graph.
- **No blockchain/Web3 libraries in Phase 1.** No wallet connectors, RPC providers, or smart contract tooling — Phase 1 has no chain interaction of any kind. (Still true for Practice Mode; the first chain dependencies arrived with Phase 2 Batch 2, confined to `lib/real/**` and `app/api/real/**` — see "Phase 2 Batch 2 Decisions".)

## Phase 2 Decisions

Made while building Batch 1 of Phase 2 (the Practice/Real boundary — see [ROADMAP.md](ROADMAP.md) for the sequencing decision that put Pay first).

- **Mode is explicit, persisted, non-financial state: `lib/stores/mode-store.ts`.** A second, tiny Zustand store (`onchain-finance:mode`) holding `mode`, `hasAcknowledgedRealIntro`, and the same explicit-rehydration `hasHydrated` flag as the simulation store. It lives outside `simulation-store` so Real Mode needs no persistence migration of the ledger and so Practice invariance can be proven by reference equality. Rejected alternatives: route-level `/real/*` routes (duplicates navigation and contradicts "same product, flip a switch"), React context (a second mechanism for what Zustand already does), and a mode field inside the simulation store.
- **The feature flag is authoritative.** `NEXT_PUBLIC_REAL_MODE_ENABLED` is read once at store creation into a non-persisted `realModeEnabled`. `selectMode`/`useMode` return Practice whenever it's off, `setMode("real")` is refused, and a persisted `"real"` is normalised back to Practice on rehydration — so a browser that remembers Real Mode from an earlier build cannot stay there after a build disables it. This is the single place the *client* enforces the flag; pages and components never check it themselves. *Corrected at S5:* it is not the only enforcement point overall. Every `app/api/real/**` route and the S4 request gate check the same variable server-side (`lib/real/server/config.ts`'s `isRealModeEnabled`) at **runtime**, while the client uses the value inlined at **build** time. The server's runtime value alone decides whether the Real API exists; the client's build-time value alone decides whether the UI offers Real Mode. A build/runtime mismatch fails closed (Real UI over a disabled API only gets 404s; a disabled UI over an enabled API still faces every route's own authentication), but the two values should always be set together. Default is off, so an unconfigured build is byte-for-byte the Phase 1 Practice-only experience.
- **Per-page boundary: `ByMode`.** Each page hands in its two parallel presentations (`practice`, `real`) and `components/shell/by-mode.tsx` picks one. With the flag off it renders Practice immediately (server-side too); otherwise it holds a neutral skeleton until the mode store has hydrated, so a Real Mode user never sees Practice flash first. Practice views were not edited to add this — only the `page.tsx` files compose it. Explore is deliberately *not* wrapped: its experiments always run on separate Practice money, and a notice says so in Real Mode.
- **Areas without a Real implementation render `PracticeOnly`** ("{Area} is Practice-only for now" plus "Try it in Practice", which switches mode and leaves the user on the same area). An intentional product state, not an error.
- **The one-time Real Mode intro** is a confirmation dialog (Base UI's alert dialog, already a dependency via shadcn) shown before the first switch into Real Mode; acceptance is persisted in the mode store. It exists for honesty — Real Mode is a testnet build with nothing of value in it — not as onboarding infrastructure.
- **Lint-enforced fences** (`eslint.config.mjs`): `simulation/**` may not import Real Mode, app stores, or chain SDKs; `lib/real/**` may not import React/Next/Zustand, the simulation, or app stores; nothing under `app/**`, `components/**`, or `lib/**` may import a chain SDK except `lib/real/**` and `app/api/real/**`. Because flat-config rule options replace rather than merge, each block carries its full `no-restricted-imports` set — composed from shared pieces in the config file.
- **Store hydration** is one root client component (`components/store-hydration.tsx`) that rehydrates every persisted store; mode first.

### Phase 2 Batch 2 Decisions — real account foundation

The account/signing stack was originally a *candidate* pointing at the Base Account SDK (see git history for that earlier text). It has since been superseded: an isolated, audited proof of concept (`poc/turnkey-real-account`; findings recorded in that branch's `TURNKEY_POC_AUDIT.md`) live-proved a different stack end to end on Base Sepolia — a real sponsored Safe transfer, confirmed on-chain, with reload/restart recovery and no persisted signing authority. Batch 2a ported the verified pure/signing layer into `lib/real/**`; account provisioning/restoration ("Phase 2 Batch 2b Decisions" below) and payment submission ("Phase 2 Batch 2d Decisions" below) are both built and live-verified. These are now **decisions**, not candidates:

- **Network:** Base Sepolia, with Circle-issued testnet USDC as the asset behind "Cash" (the internal symbol stays `USDC`; "Cash" remains a presentation label, as in Phase 1). Still unverified: the Sepolia-family sunset timeline and Base's plan for it — unrelated to the account-stack question and not addressed by the PoC.
- **Account/signing:** a passkey-backed Safe smart account, *not* the Base Account SDK. A user's WebAuthn passkey directly authorizes a Turnkey-controlled secp256k1 key (child sub-organization; no Turnkey session/login credential, no IndexedDB stamper), which owns a Safe 1.4.1 smart account (threshold 1, Safe4337Module 0.3.0, EntryPoint 0.7). Every signature requires a fresh WebAuthn ceremony; the app never holds key material. **Important finding carried forward:** `@turnkey/viem`'s own `signTypedData` adapter was proven live to recover the wrong address. Real SafeOp signing therefore goes: `viem.hashTypedData` (local) → Turnkey `signRawPayload` (`PAYLOAD_ENCODING_HEXADECIMAL` + `HASH_FUNCTION_NO_OP`) → `recoverTypedDataAddress` (local) → require the recovered address to equal the canonical owner before ever returning a signature (`lib/real/signing/verified-account.ts`), independently re-checked against the fully-packed SafeOp signature before submission (`lib/real/payments/safe-op-preflight.ts`). `@turnkey/viem` itself is consequently **not a dependency**: `permissionless`'s `signUserOperation` only ever calls `.address` and `.signTypedData()` on the owner (verified against installed package source), so the account is built directly on plain viem's `toAccount()` — the broken adapter isn't merely unused, it isn't installed.
- **Gas:** sponsored via Pimlico (bundler + paymaster), reached only through a server-side route handler that holds the Pimlico API key — never sent to the browser. The PoC's dev proxy allow-listed RPC *methods* only, which its own audit flagged as insufficient (arbitrary sender/calldata could ride on a valid app session). **This is now implemented, not a TODO:** the production route validates sender-binding (`prepare`'s derived-sender check against the session's registry `safeAddress`, Pre-2f Hardening Decisions below), hardcodes token/chain/calldata shape (Batch 2d), and applies per-account sponsorship rate limits via the durable quota system (Batch 2d's `reserve()`).
- **Client library:** viem for reads, encoding, types, and account construction; `permissionless` for the Safe/ERC-4337 account and UserOperation signing/packing. wagmi/RainbowKit remain not proposed (wallet-picker UX contradicts the product; hooks in components would defeat the `lib/real/` boundary).
- **TypeScript target:** `ES2017` today; whether to move to `ES2020` (bigint literals) is decided when a bigint-heavy dependency actually lands.

### Phase 2 Batch 2b Decisions — registration, restoration, and durable storage

- **App authentication is independent of Turnkey.** Our own WebAuthn verification (`@simplewebauthn/server`) plus an HttpOnly, HMAC-signed app session (`lib/real/server/session.ts`) decide who's logged in. Turnkey is never asked to authenticate a login — its native session-login primitives (`stampLogin`, `createReadWriteSession`, `loginWithPasskey`, IndexedDB signing sessions) are not used anywhere in this codebase. One WebAuthn registration ceremony produces the credential used for both our verification and (only after that succeeds) Turnkey child sub-organization provisioning — never two separate passkeys *at account-provisioning time*. Batch 2g (below) deliberately supersedes the stronger "never" this bullet used to make: an account may now gain a second, independently-verified passkey against the *same* Turnkey user, after provisioning.
- **Durable storage: Neon Postgres**, reached only through server-only `@neondatabase/serverless`, behind the same vendor-neutral `RealAccountRegistry` / `ChallengeStore` / `RegistrationAttemptStore` interfaces used by the in-memory test adapters (`lib/real/server/neon-store.ts` vs. `challenge-store.ts` / `registry.ts` / `registration-attempts.ts`). Selected by `DATABASE_URL` at runtime (`lib/real/server/runtime.ts`); in dev/test, unset falls back to in-memory, which resets on restart. **Production fails closed without `DATABASE_URL`** — see "Phase 2 Pre-2f Hardening Decisions" below. No Redis/Upstash: nothing yet needs it. Database code stays server-only and behind these interfaces; it never leaks into components, `lib/real` signing/domain modules, or Zustand stores.
- **Registration is a durable state machine**, not a single request/response: `verified → provisioning_in_flight → turnkey_created → active`, with a terminal `blocked` state for ambiguous reconciliation (`lib/real/server/registration-attempts.ts`, driven by `lib/real/server/onboarding.ts`'s `runProvisioningPipeline`). The WebAuthn-verified credential and its raw ceremony artifacts are persisted *before* the external Turnkey `createSubOrganization` call, so a crash between "Turnkey child created" and "local record written" is reconcilable rather than silently orphaning a real Turnkey child. A separate `externalOutcome` field (`not_attempted` / `unknown` / `confirmed_created` / `definitive_failure`) tracks the external call itself: it is set to `unknown` durably, in the same write that moves the attempt into `provisioning_in_flight`, *before* `createSubOrganization` is actually dispatched — so even a crash between that write and the network call leaves a durable "unknown," never a false "not_attempted."
- **Never a blind repeat, and (since S5 L2) never an automatic adoption.** Once an attempt's `externalOutcome` is `unknown`, nothing may call `createSubOrganization` again for it automatically. The **one** condition that may trigger a fresh create is a **Turnkey-confirmed definitive failure**: a terminal `ACTIVITY_STATUS_FAILED` or `ACTIVITY_STATUS_REJECTED` of that dispatch's own activity, read by its exact id (`@turnkey/http` 6.5.0 exposes no client-chosen idempotency key). Every other outcome (network error, timeout, any non-2xx answer, an unreadable answer, `CONSENSUS_NEEDED`/`AUTHENTICATORS_NEEDED`, a poll that ran out of time) is `unknown`. Since "Provisioning Evidence Capture" (below) the create no longer goes through the SDK's `createActivityPoller`; the rule is unchanged. Batch 2b originally resolved `unknown` by Turnkey credential discovery (`getSubOrgIds` + shape); **S5 L2 removed that** (see "L2" under S5). An uncertain create now stays `provisioning_in_flight`, reported as needing review, with no Turnkey call, until a future operator-only resolver exists.
- **A pending (non-active) registration is resumable via a normal login.** Because the durable attempt row holds the credential's public key, counter, and userHandle, a later valid APP WebAuthn login assertion for that credential independently re-verifies possession and resumes the same `runProvisioningPipeline` — without a second WebAuthn ceremony and without ever issuing a session before finalize. It completes `verified` (definitive-failure retry) and `turnkey_created` attempts; an uncertain (`provisioning_in_flight`) attempt stays needs-review.
- **Live-verified, not just tested offline.** One real registration and one fresh-browser (separate incognito profile) restore were run against Base Sepolia, a real Turnkey parent organization, and a real Neon database: a single passkey ceremony produced one `registration_attempts` row (`state: active`), one `real_accounts` row, and one `real_passkeys` row — confirmed by direct read-only inspection of the live database, with no duplicate or orphaned rows — and the fresh-browser login independently re-verified the same passkey and restored the identical owner/Safe address pair. This closes out Batch 2b.
- **Resolved in Batch 2d:** the acceptance check that a valid app session alone can never authorize a payment — i.e., that submitting Cash requires its own fresh, separate Turnkey WebAuthn ceremony at signing time, independent of the app-login session above. Proven end-to-end against a real payment; see "Phase 2 Batch 2d Decisions" below.

### Phase 2 Batch 2c Decisions — real Cash balance (read-only)

- **Asset:** Circle-issued testnet USDC on Base Sepolia, address `0x036CbD53842c5426634e7929541eC2318f3dCF7e`, 6 decimals (`lib/real/constants.ts`'s `REAL_CASH_TOKEN`) — cross-checked against Circle's published testnet contract addresses, not taken on faith. Consumer-facing rename to "Cash" and all display formatting live in `lib/real/display/cash.ts`, kept out of the domain/constants layer (same domain/presentation boundary Practice's `lib/format.ts` already keeps).
- **Layering, preserved exactly:** `CashBalance` component → `lib/stores/real-balance-store.ts` (fetch only, unpersisted) → `app/api/real/account/balance/route.ts` → `lib/real/server/balance.ts`'s `resolveAuthenticatedCashBalance` → `lib/real/chain/balance.ts`'s `readCashBalance` → a viem `PublicClient` → Base Sepolia. No component imports viem; only `lib/real/chain/**` does.
- **The Safe address is always server-derived, never client-supplied.** The balance route takes no request body or query parameters at all; the address read is whatever `readAuthenticatedRealAccount` (the same HttpOnly-session → registry resolution Batch 2b's login uses) returns as the session's `RealAccountRecord.safeAddress` — never the Turnkey owner address, never anything a caller could name.
- **Chain/contract/decimals are validated on every read, not assumed.** `readCashBalance` calls `getChainId()` against the live RPC (not just the locally-configured `chain` object) and rejects anything other than Base Sepolia; it also reads the USDC contract's own `decimals()` and rejects a mismatch against the configured `6` — both exist specifically so a misconfigured RPC URL or the wrong contract can never silently produce a balance.
- **An RPC/read failure is never displayed as `$0.00`.** `resolveAuthenticatedCashBalance` returns a distinct `read_failed` outcome (mapped to HTTP 502) that the client store keeps as a separate `error` status with `balance: null` — the UI shows an explicit error + retry, never a fabricated zero. A genuine on-chain zero balance is its own `ready` outcome, formatted normally.
- **No signing surface at all.** This read path imports no `@turnkey/*`, no `permissionless`, nothing Pimlico-related — verified both by an explicit source-content test and by the existing repo-wide `lib/real/**` boundary sweep (`test/lib/real/boundary.test.ts`).
- **Live-verified:** an authenticated request against the real Batch 2b account, on the real (currently unfunded) Safe, returned a genuine on-chain `$0.00` — the correct, honest first result, not a placeholder or an error being mislabeled as zero. Manual refresh confirmed on both Real Home and Real Pay.

### Phase 2 Batch 2d Decisions — Real Pay (send)

- **Three-call flow, not one:** `POST /api/real/payments/prepare` (server, secret-holding) → client-side signing → `POST /api/real/payments/submit` (server). This isn't stylistic — it falls directly out of two constraints that can't both be satisfied by a single call: the server must bind Pimlico sponsorship to a specific, already-validated intent (never sponsor an arbitrary browser-supplied UserOperation), and signing must happen in the browser (WebAuthn cannot run in Node). `prepare` derives the sender from the session, hardcodes token/chain, validates recipient/amount (including a $50-per-payment ceiling, `lib/real/payments/amount.ts`), re-reads the live balance, and only then asks Pimlico to sponsor a UserOperation whose calldata it built itself (`lib/real/server/pimlico.ts` — `to` is always `REAL_CASH_TOKEN.address`, hardcoded, no parameter can redirect it). `submit` takes only `{attemptId, signature}` — every other field is read back from the server's own durable row, never re-trusted from the client.
- **Fresh WebAuthn per payment, no persistent signing authority.** The client rebuilds the Safe account object and calls `signUserOperation` for every payment (`lib/real/payments/client-sign.ts`), which drives Batch 2a's proven pipeline (`hashTypedData` → Turnkey `signRawPayload` with `PAYLOAD_ENCODING_HEXADECIMAL`/`HASH_FUNCTION_NO_OP` → `recoverTypedDataAddress` against the canonical owner) — a fresh `TurnkeyClient`/`WebauthnStamper` every call, nothing cached. A valid app session cookie is identity only; it cannot itself produce or approve a signature, verified end to end by `resolveSubmitPayment` requiring an independently-verifying signature before ever touching the bundler.
- **Durable payment state machine with a pre-dispatch "submitting" checkpoint:** `prepared → awaiting_authorization → signed → submitting → submitted → confirmed`, with `failed`/`cancelled`/`unknown` as alternates (`lib/real/server/payment-attempts.ts`). The `signed → submitting` CAS transition is written **before** `eth_sendUserOperation` is ever called — closing the crash window between "signature verified" and "we know what happened": a process death anywhere from there through recording the dispatch result leaves a durable `submitting` row, reconciled the same way `unknown` is (via the precomputed hash), never resent. Only the CAS winner of `signed → submitting` may dispatch.
- **Reconcile, never blindly resend.** `expected_user_operation_hash` (viem's `getUserOperationHash`, EntryPoint 0.7) is computed and persisted in `prepare`, before any dispatch — the signature isn't part of this hash, so it's fully knowable ahead of signing. A bundler-returned hash that doesn't match is treated as `unknown`, never trusted at face value. Reconciliation (`resolvePaymentStatus`) is the only path out of `submitting`/`submitted`/`unknown`, and only ever moves an attempt to `confirmed`/`failed` on a receipt whose hash and sender both match. The raw signature itself is never persisted — used once in-process during `/submit`, then discarded. **Conservative by design:** an attempt with no definitive receipt (stuck at `submitting`/`unknown`) stays exactly there — blocking the account's one-active-attempt slot — until a receipt unambiguously resolves it; there is no automatic retry, resend, or timeout-based resolution (deferred; see Pre-2f Hardening Decisions).
- **Atomic reservation in Neon, not application-level locking — corrected (Pre-2f Hardening).** `PaymentAttemptStore.reserve()` is a single SQL statement — a transaction-scoped `pg_advisory_xact_lock` forced to execute via a `MATERIALIZED` CTE cross-joined into the quota count — so no caller can observe a "count says OK" result and then race a second INSERT past it. Two independent audits (2026-09) corrected an overclaim here: the lock does *not* refresh this statement's read-committed snapshot, so a row committed by a competitor while this statement was waiting on the lock isn't guaranteed visible to the count once it resumes — the hourly/daily numeric quota is therefore serially enforced and best-effort precise, not a mathematically airtight bound. What *is* unconditional is the one-active-payment-per-account invariant, enforced independently by the partial unique index `payment_attempts_one_active_per_account` — a hard Postgres constraint checked against committed reality at INSERT time, not any statement's snapshot — so quota is never bypassable in the way that would matter (two active payments at once). See `lib/real/server/neon-store.ts`'s doc comment for the full correction. Proven against real Neon concurrency in `test/lib/real/neon-smoke.test.ts`, not just in-process. If a future design ever allows more than one active payment per account, this reservation logic must be revisited.
- **One shared wire type crosses the server/browser boundary, not two look-alikes.** `lib/real/payments/prepared-operation.ts`'s `WirePreparedFields` is imported directly by both `lib/real/server/payments.ts` (the HTTP response shape) and `lib/real/payments/client-sign.ts` (what the browser signs from) — never independently re-declared on either side. This is a corrected decision: an earlier, separately-declared server-side type omitted `sender`, which silently produced `undefined` in the browser (`fields.sender.toLowerCase()` threw before any WebAuthn ceremony) — a defect no static type check could catch across an HTTP boundary between two structurally-different types. Regression-tested end to end (`test/lib/real/payments-wire-shape.test.ts`): a real server response, JSON round-tripped, fed into real client-side signing.
- **No generic Pimlico proxy.** The Pimlico API key is reached only from `lib/real/server/pimlico.ts` and the payment route handlers that pass it through — never a route that forwards arbitrary client-supplied JSON-RPC method/params, unlike the audited PoC's dev-only proxy.
- **Live-verified end to end:** one real sponsored Cash transfer ($0.01) on Base Sepolia — `/prepare` → fresh Turnkey `signRawPayload` → `/submit` → `/status` → balance refresh, UI showing "Sent", a `confirmed` Neon row with a populated `transaction_hash`, and a prior stale `awaiting_authorization` attempt safely cancelled (not resent) beforehand.

### Phase 2 Batch 2e Decisions — Real Pay transaction history (read)

- **`payment_attempts` doubles as the bounded app-payment history source — it is not a universal chain indexer.** History means "payments made through this app/account flow," not "all on-chain activity ever associated with this Safe": no Transfer-log scanning, no second activity database. Served by the same `(app_user_id, created_at DESC)` index Batch 2d's `findLatestByAppUserId` already uses, via a new sibling read method, `findRecentByAppUserId({ appUserId, limit })`, on both the in-memory and Neon `PaymentAttemptStore` adapters — no schema change.
- **A physically separate read module, not an addition to `server/payments.ts`.** `server/payments.ts` owns prepare/submit/status orchestration and everything that comes with it — Pimlico, signing verification, reconciliation. Pulling history through that module would make the read path structurally depend on the write/signing module graph even if no history code actually called into it. `lib/real/server/payment-history.ts` is deliberately separate: it depends only on `readAuthenticatedRealAccount`, `RealAccountRegistry`, and `PaymentAttemptStore`, and never imports `pimlico.ts`, `submit.ts`, `client-sign.ts`, or any Turnkey/signing module. `GET /api/real/payments/history` imports only this module — `route → payment-history.ts → auth/store → database read`, never through `payments.ts`'s mixed read/write orchestration. Enforced by an explicit boundary test (`test/lib/real/boundary.test.ts`), not just convention.
- **A thinner public shape than `PublicPaymentAttempt`.** `payments.ts`'s `PublicPaymentAttempt` carries `prepared: WirePreparedFields | null` — nonce/calldata/gas/paymaster, needed only to sign. History's `PaymentHistoryEntry` (id, recipient, amountBaseUnits, state, transactionHash, createdAt, updatedAt — plus, since Slice D, `recipientIdentity`) has no such field, and its mapper (`toPaymentHistoryEntry`) is independent of `toPublicAttempt`. `failureReason` is excluded too — it remains an internal field (now always one of a small set of fixed, safe strings, per "Fixed, safe error messages" below) — so a failed/cancelled/unknown row exposes only its state; the UI maps that to a generic label, never the internal reason.
- **Authenticated and account-scoped the same way the balance/latest routes already are:** no request body, no account/appUserId parameter at all — the only input is `limit`. The account is always whatever the session resolves to, so "a client cannot request another account's history" is true structurally, not just by a runtime check.
- **Bounded limit, clamped rather than rejected:** default 10, hard max 25 (`clampHistoryLimit`). Missing/invalid input falls back to the default; anything above the max is capped at it — no separate "bad limit" error path for the client to handle.
- **Status language is a presentation-layer mapping, not a rename in the state machine** — same domain/presentation boundary `lib/real/display/cash.ts` already keeps. `lib/real/display/payment-status.ts`'s `paymentStatusLabel()` maps the 9-state machine to consumer language (confirmed→"Sent", submitted/submitting→"Sending", unknown→"Checking status", failed→"Failed", cancelled→"Cancelled", awaiting_authorization/prepared/signed→"Pending approval") over a client-safe `PaymentDisplayState` union — the same deliberate duplication of the state list `real-payment-store.ts`'s `RealPaymentAttemptState` already makes, so a client-facing module never imports the server-only type.
- **Strictly passive — no reconciliation call from the history UI.** `GET /api/real/payments/[id]/status` already exists and can mutate durable state (Batch 2d's reconciliation). History deliberately does not call it: the client store (`real-payment-history-store.ts`) has exactly one action, `fetchHistory()`, used for both the initial load and the Refresh button, and never calls `/prepare`, `/submit`, `/cancel`, or `/status`. Non-final rows are shown truthfully with their current state; resolving them stays the job of Batch 2d's active-payment flow, not this read view.
- **No new authority or signing surface.** No new session type, no new mutation path, no new database table — this batch is presentation over data Batch 2d already writes.
- **Live-verified, in two parts.** An independent audit's findings (malformed-response handling, explorer-hash validation, boundary-test strength, deterministic Neon ordering) were fixed first; then: (1) a real-Neon smoke test (`test/lib/real/neon-smoke.test.ts`) proved `findRecentByAppUserId` newest-first, limit-honoring, and account-scoped against actual Postgres, alongside the rest of that gated suite (13/13); (2) a live, read-only browser check against Base Sepolia + the real Neon database confirmed the existing confirmed ($0.01) row renders "Sent" with a working explorer link to the real transaction, the existing cancelled row renders "Cancelled," and Refresh produces exactly one `GET /api/real/payments/history?limit=10` call — no `/prepare`, `/submit`, `/cancel`, or `/status`. No live payment was made and no WebAuthn/Pimlico call was invoked to perform this verification.

### Phase 2 Pre-2f Hardening Decisions

Prompted by two independent audits (Fable 5.1 High, Grok 4.7 High) of the branch at commit `67a5a64`, ahead of Batch 2f (the final repo-wide audit, docs, PR, and merge — unchanged in scope by this pass). Not a product batch: no new Real Mode surface, just correctness/security hardening of what Batches 2a–2e already built.

- **Fixed, safe error messages — never raw upstream text.** `resolvePreparePayment`'s balance-check and Pimlico-prepare failures, `resolveAuthenticatedCashBalance`'s RPC failures, and `safe-op-preflight.ts`'s signature-recovery failure all used to persist/return `error.message` directly. Since Pimlico's and the RPC provider's URLs are API-key-bearing, and viem's `HttpRequestError`/`RpcRequestError.message` embeds the request URL via `metaMessages`, this could leak a live secret into `payment_attempts.failure_reason` (durable) and an HTTP response. Every one of these paths now returns one of a small set of fixed, hardcoded strings instead — never `error.message`, and, per explicit design choice, never `error.shortMessage` either (not relied on as the durable/public contract even though it's usually secret-free). `classify-send-error.ts`'s bundler-rejection classification keeps its `stage` logic (which named rejection matched) but now returns one of two fixed strings for `detail`, deliberately losing per-category detail (e.g. "insufficient prefund" vs "nonce too low") in exchange for the same guarantee. No diagnostic logging was added to compensate — the simplest correct fix.
- **Every `app/api/real/**` route's generic exception handler is now a single fixed message.** `lib/real/server/http.ts`'s new `jsonInternalError()` replaces `jsonError(asErrorMessage(error), 500)` everywhere — closing off `requireRealServerConfig()`'s "missing env var names" text, raw Postgres errors from an unvalidated id, and any other unexpected exception from ever reaching a client. A new `readJsonBody()` helper turns a malformed JSON request body into a clean 400 instead of falling through to that same catch-all. A new `isValidUuid()` (`lib/real/identifiers.ts`) is checked before every `attemptId`/`id` reaches a store lookup, turning what used to be a raw `invalid input syntax for type uuid` Postgres error into the existing `not_found`/404 outcome.
- **Pre-dispatch states can no longer strand an account.** `resolveSubmitPayment` used to run `toPreparedFields` and `verifyPreparedPaymentSignature` — between the `awaiting_authorization → signed` and `signed → submitting` CASes — with no try/catch; a throw there (a corrupted stored row, an unrecognized signature-recovery failure) left the row at `signed` forever: not resendable, not reconcilable (`RECONCILABLE_STATES` never included `signed`), and — since cancel only accepted `awaiting_authorization` — not cancellable, permanently occupying the account's one-active-attempt slot. Fixed two ways: a pre-CAS hex-format check on the signature (new `invalid_signature` outcome, 400) refuses structurally malformed input before it ever claims the row, and the entire signed-window is now wrapped in try/catch, CASing to a terminal `failed` (fixed safe reason) on any throw. `resolveCancelPayment` now accepts `prepared`/`awaiting_authorization`/`signed` (previously only `awaiting_authorization`) as the last line of defense, CAS'ing from the attempt's own current state — this is also what makes the cancel-vs-submit race resolve correctly: whichever CAS (cancel's `→ cancelled` or submit's `signed → submitting`) commits first wins, and the loser's own CAS then fails, so cancel winning means the bundler is never called, and submitting winning means cancel is refused. `submitting`/`submitted`/`unknown` remain permanently non-cancellable — the operation may already be on-chain. The client (`real-payment-store.ts`) gained a `"stranded"` status (mapped from a reload-observed `prepared`/`signed` row) offering only Cancel — no resend/retry.
- **Account-switch/logout state isolation.** `real-payment-store.ts` had no subscription to account identity at all; `real-pay-form.tsx`'s effect only called `init()` on a truthy account, never resetting on logout, so a prior account's typed recipient/amount could survive into a newly signed-in account. Fixed by having `init()` reset `recipientInput`/`amountInput`/`attempt`/`error`/etc. as its first action (holds regardless of caller), and giving the component's effect the same `if (account) fetch else reset()` shape `cash-balance.tsx`/`real-payment-history.tsx` already used — which themselves gained an unconditional `reset()` before every fetch, closing the smaller gap where a truthy-to-truthy address switch could briefly leave `status: "ready"` with the prior account's balance/history.
- **Production fails closed without `DATABASE_URL`.** `lib/real/server/runtime.ts` previously fell back to fully in-memory, single-process stores whenever `DATABASE_URL` was absent, with no `NODE_ENV` check — a misconfigured production deployment would silently run non-durably. It now throws a clear configuration error when `NODE_ENV === "production"` and `DATABASE_URL` is unset, surfaced to callers as the generic 500 above; the in-memory fallback is unchanged for local/test use.
- **Derived-sender consistency check at prepare time.** `prepareCashTransferUserOperation` returns its own derived `sender` (permissionless's computed Safe address), which `resolvePreparePayment` previously never read or compared — every downstream use of "the sender" pulled from the durable, session-derived `safeAddress` instead, silently discarding what was actually prepared. `resolvePreparePayment` now asserts `addressesEqual(prepared.sender, safeAddress)` immediately after preparing, failing closed (before the user is ever asked to sign) on any mismatch.
- **Route-handler tests, not just resolver tests.** Three representative routes (`prepare`, `[id]/cancel`, `latest`) are now exercised as actual `route.ts` `GET`/`POST` exports (mocking `next/headers`'s `cookies()` and stubbing the handful of required env vars) proving malformed-JSON→400, malformed-id→404 without a raw DB error, and an unexpected internal exception→a generic fixed 500 body — supplementing, not replacing, the existing resolver-level test convention.

### Phase 2 Batch 2g Decisions — backup passkey (add, verify, remove a second credential)

A bounded security slice built after Phase 2 closed: an account may enroll a second (backup) WebAuthn passkey against the *same* Turnkey user in the *same* child sub-organization — never a new Turnkey user, never a Safe owner/threshold change, never a new Safe address. This improves **availability** (another way in if one device is lost). It is not disaster recovery: **losing every passkey on an account remains unrecoverable** — no email/SMS/OTP/guardian recovery and no Safe owner rotation exist. Primary and backup are labels only; once active they have **equal** Turnkey authority.

- **Model B dispatch — the child WebAuthn stamp is the only authority.** Turnkey mutations (`ACTIVITY_TYPE_CREATE_AUTHENTICATORS_V2`, `ACTIVITY_TYPE_DELETE_AUTHENTICATORS`, both confirmed in `@turnkey/http@6.5.0`) are never dispatched by the browser. The browser only *stamps* the exact activity the server built from durable state (`stampCreateAuthenticators` / `stampDeleteAuthenticators`, `lib/real/signing/authenticator-requests.ts`) with a fresh WebAuthn ceremony scoped to one credential — always the caller's **session credential**, derived server-side, never client-selected. The server (`lib/real/server/turnkey-signed-request.ts`) then: rejects the signed body (and the stamp header value) if the **raw text** is not strict JSON or repeats a member name in any object at any depth — compared after escape decoding, so `"foo"` and `"foo"` collide — because `JSON.parse` is last-key-wins and Turnkey's parser may not be, and these exact bytes are forwarded (a read-only scan, never parse-and-reserialize); validates the exact body string against authenticated durable state (org, Turnkey user, credential/attestation or exact target authenticator id, activity type, no extra fields, timestamp freshness); validates the browser-reported URL against the one server-configured endpoint for that activity; **cryptographically verifies the stamp** is a user-verified assertion by the expected credential's stored public key over exactly that body (the stamper's challenge is `utf8(hex(sha256(body)))`); CASes the durable row into an in-flight state with `externalOutcome = unknown` and the exact request recorded **before** any external call; and only then raw-`fetch`es the byte-identical body with the original stamp header. Never `TurnkeyClient.request` (it re-stringifies and re-stamps). The parent API key is never attached to these activities; its authority is unchanged — read-only `getUsers` / `getActivity` for reconciliation.
- **Unknown outcomes are reconciled, never blindly repeated.** A lost response may lead only to a **byte-identical replay while the stamp is fresh** (a conservative *local* 2-minute window — Turnkey's own timestampMs freshness rule and its same-body fingerprint dedupe are **unverified candidate facts**), then read-only `getActivity` polling (bounded, client-driven; `PENDING` stays pending) and `getUsers`. The stored stamp — a live, body-bound bearer credential — is cleared as soon as an activity id is recorded or the window closes. The server never re-stamps or mints a new timestamp on its own; for enrollment, a dispatched create is never re-authorized (2g-H: even a `FAILED`/`REJECTED` activity doesn't prove the browser-held signed request can't still land); a dispatched removal is never re-authorized automatically (see below).
- **Enrollment** (`backup_passkey_enrollments`, `lib/real/server/backup-passkey-pipeline.ts`): `started → credential_registered → turnkey_enrollment_in_flight → turnkey_authenticator_created → login_verified → active`, off-ramps `abandoned` (only while no Turnkey authority can exist; the orphan pending passkey is revoked, truthfully) and — as revised by 2g-H below — the non-terminal `blocked` review, `removal_in_progress`, and terminal `removed`. Registering the new credential inserts the pending passkey and attaches it to the enrollment in **one transaction**. A COMPLETED create activity is accepted only when `getUsers` shows exactly one authenticator for the new credential — matched by **decoded credential-id bytes** (`lib/real/credential-id.ts`; malformed ids never match, no raw-string fallback) — whose id equals the activity's result. With no activity id ever learned and the window closed, an exact byte match confirms; a miss is **not** proof of failure and stays pending/unknown.
- **Two independent proofs before a backup is usable.** (A) The new credential completes an app-login assertion against a single-use, account/enrollment-bound challenge whose `allowCredentials` is only that credential — evidence only, never a session. (B) The new credential authorizes a `signRawPayload` over a random enrollment nonce; the server reads that activity back (read-only) and requires it be COMPLETED in the same org, sign exactly that nonce with the canonical owner, carry an **APPROVED vote whose `publicKey` equals the new authenticator's `credential.publicKey`** (recorded from `getUsers` at creation) — so the primary's vote cannot satisfy it — **and** its signature must recover to the canonical owner. Nothing is broadcast; no UserOperation, no Safe nonce. Activation (passkey `pending → active` + enrollment `→ active`) is **one transaction**.
- **Removal** (`passkey_revocation_attempts`, `lib/real/server/passkey-revocation.ts`): `authorization_needed → dispatch_in_flight → confirmed`, off-ramps `cancelled` (before dispatch only) and `blocked` (after dispatch). **An app cookie alone disables nothing:** preparing a removal only records an `authorization_needed` attempt bound to the session credential (the surviving authorizer, never client-selected); the target stays `active`, and only that session credential may cancel it. The target leaves `active` only after the survivor's fresh `stampDeleteAuthenticators` request is verified (body, URL, stamp over the exact bytes) — then **one transaction** locks the account row (`SELECT … FOR UPDATE`), re-reads target and survivor, requires the survivor still active, Turnkey-mapped and ≠ target, moves the attempt to `dispatch_in_flight` with the exact request, and moves the target `active → revoking`, committed before the forward. So racing "remove A using B" / "remove B using A" can never leave zero active credentials, and a cancelled WebAuthn prompt leaves the target active. **App disabled ≠ Turnkey removed:** `revoking` means a verified delete was dispatched and isn't confirmed — the UI says the passkey *may still authorize at Turnkey*. **`revoked` requires BOTH** a COMPLETED delete activity whose result names exactly the target authenticator **AND** a subsequent read showing it absent; a discovery miss alone is never a deletion receipt. **One-way after dispatch:** once a verified signed delete is accepted, the browser holds valid bytes it could send to Turnkey itself, so no outcome the server observes — a `FAILED`/`REJECTED` activity (from any send), no activity id, or a positive `getUsers` read (which may be stale) — proves the target wasn't deleted. A dispatched target therefore never returns to `active`; there is no restore operation in either store. The only exits from `dispatch_in_flight` are `confirmed` (both halves of the evidence above) or `blocked`: the target stays `revoking` (app sign-in off, *may still authorize*) and is never claimed Removed. Nothing is ever retried automatically; since 2g-H the user may authorize a **new** attempt for it (see below). Before dispatch — a cancelled prompt, an explicit cancel, or a refused stamp/body — the target never left `active`.
- **A failed create is not proof of absence.** After a lost response, the activity observed may be a byte-identical replay while the original request succeeded (Turnkey same-body dedupe is **not** assumed). So on FAILED/REJECTED the enrollment first reads `getUsers`: an exact credential-byte match confirms creation, an ambiguous result blocks, and — since 2g-H — a clean miss is **review**, never a re-authorizable state (the browser still holds the signed create; see 2g-H below).
- **Neon atomicity mechanism.** `@neondatabase/serverless`'s `sql.transaction()` is a non-interactive batch, so each multi-row Batch 2g operation ends with a guard `SELECT` that casts a row-dependent string to `int` only when the batch outcome is inconsistent (a lost race) — the resulting error rolls the whole batch back. **Live-verified against real Neon** through the `DATABASE_URL`-gated smoke suite: racing A↔B dispatch under `FOR UPDATE`, racing pending-credential registration, whole-batch rollback in `confirmCreated` and activation, first-writer-wins activity recording, and the no-restore state CHECK.
- **Pre-2g primaries need a Turnkey mapping before they can be removed or authorize a removal.** `lib/real/server/backfill-turnkey-authenticator-ids.ts` (read-only Turnkey, byte matching, writes only unambiguous matches with `turnkey_authenticator_id IS NULL`, reports and never overwrites conflicts, rerunnable) is run only through the explicitly opt-in admin runner `test/admin/backfill-turnkey-authenticator-ids.admin.test.ts` — no extra dependency. It **was run live successfully** against the real Neon database and Turnkey parent org, before the live primary-removal test.
- **Passkey names are presentation metadata only.** `real_passkeys.display_name` (nullable, 1–40 characters by DB CHECK, not unique, not indexed) is never used in any lookup, session, stamp check, or removal — identity stays `credential_id` / `turnkey_authenticator_id`. No name is stored at enrollment or registration (those SQL paths are unchanged); `passkeyDisplayName()` (`lib/real/display/passkey-name.ts`) falls back to the role label, so pre-existing rows need no backfill. No device detection: the browser can't reliably tell "MacBook Touch ID" from "iPhone", so the user names it. `PATCH /api/real/account/passkeys/[credentialId]` renames with an app session alone — the name changes no identity, status, or authority — and the single `UPDATE` requires both `app_user_id = session` and `status = 'active'`; another account's credential gets the same 404 as a missing one. Input is NFC-normalized, trimmed, non-empty, control-character-free, ≤ 40 code points (shared validator on client and server).
- **The sole survivor is the primary; revoked passkeys are hidden, never deleted.** Role stays app metadata only. A credential added to an existing account is always `backup`. `confirmDeleted` — the one transaction that marks a removal confirmed and its target `revoked` — also promotes the account's oldest active passkey to `primary` when no non-revoked primary is left. On Neon it takes the same per-account `FOR UPDATE` lock as `beginDispatch` and ends with a guard that rolls the whole batch back rather than commit "confirmed" with an active survivor and no primary. A dispatched but unconfirmed removal promotes nothing, because the old primary may still authorize. Promotion never touches status, credential or authenticator identity, Turnkey, owner, or Safe. Revoked rows stay in `real_passkeys` as audit history (removal attempts reference them); the management list and UI omit them, while pending/revoking rows stay visible as live operations. `schema.sql` carries an idempotent, hand-applied one-time repair using the same rule for removals confirmed before this change.
- **Schema migration.** `schema.sql` drops and re-adds the `status`/`purpose` CHECK constraints by *discovering* their live names (the original inline CHECKs' auto-generated names are not assumed), atomically, in `DO` blocks; the exact read-only pre-live verification query is in the file.
- **Deliberately unchanged (in 2g):** SafeOp `validAfter`/`validUntil` (then still `0`/`0` — see "Finite SafeOp expiry" below), nonce reconciliation, Real Pay semantics (`signDigestViaTurnkeyRaw` now also returns its activity id; the payment path ignored it until Slice S1 — see "Real Pay Credential Attribution" below), Practice Mode. No Turnkey webhooks: the durable-record + read-only-poll pattern needs no push signal.
- **Live-verified (Base Sepolia, a real Turnkey child org, real Neon):** Neon concurrency/atomicity (above); exact-byte forwarding of child-stamped create and delete activities; parent-key `getActivity` on child activities; `vote.publicKey` equal to the backup authenticator's `getUsers` `credential.publicKey`; Proof A; Proof B; sign-in with only the backup; a Real Pay payment authorized by the backup; a cancelled removal; an actual primary removal; sign-in with the survivor; passkey naming and survivor promotion.
- **Still unverified candidates:** Turnkey's own `timestampMs` freshness rule and whether it dedupes a same-body replay (the local 2-minute window and the "never assume dedupe" handling above stay conservative for that reason), and the lost-response / `blocked` reconciliation paths, which are proven offline only. Not mainnet-ready.

### Batch 2g-H — backup setup step-up + the unresolved-authority lifecycle

A security slice on Batch 2g, from an adversarial audit of `aabd4f3` and two independent reviews of its first draft. No change to Turnkey authority semantics, the owner, the Safe, Real Pay, or Practice Mode.

**The invariant.** A credential that *may* hold Turnkey authority is never shown as harmless, is always either removable or reconcilable, and keeps holding the account's one-open-enrollment slot until its absence is *proven* — so an account can't pile up replacement backups around unresolved authority.

- **H1 — a stolen cookie planting a passkey.** A backup's credential is *chosen* at registration, and the later Turnkey authorization is bound (exact body) to it. Registration used to need only the app cookie, so a cookie thief could register their own authenticator and one innocent "Resume setup" tap by the victim would give it full wallet authority (at the time Real Pay's signing wasn't pinned to a credential and the server only checked owner recovery — Slice S1 below changed that, but a planted authenticator would still hold Turnkey wallet authority outside this app).
- **Step-up before every registration challenge.** `POST /backup/step-up/options` issues sign-in options for the **current session credential only** (`userVerification: required`, purpose `backup_step_up`, single-use, 5-minute TTL, context bound to app user + credential). `POST /backup/options` verifies that assertion (credential bytes, user handle, UV, signature, counter) before creating an enrollment or re-minting a `started` one — every call needs its own step-up. Each mint gets a fresh `registration_mint_id` (CAS while `started`); the registration challenge carries it and `stepUpCredentialId`, and `/backup/register` attaches a credential only for the **current** mint (checked again atomically in the store), from that same, still-active session credential — any earlier challenge is superseded. `registration_step_up_credential_id` is recorded, and both Turnkey-authorization entry points require it to **equal the current session credential** (a setup step-upped by A can't be authorized from B; a row without it — only possible pre-2g-H — can only be cancelled).
- **H2 — pending but live at Turnkey.** From `turnkey_authenticator_created` through `login_verified` the pending backup is a live, mapped Turnkey authenticator. It is now removable by a different, active, mapped passkey with a fresh survivor stamp, exactly like an active one.
- **The slot frees only on proven absence.** Dispatching that removal moves the enrollment to **`removal_in_progress`** in the same locked transaction as the passkey `pending → revoking`: activation (and Proof A/B) becomes impossible immediately, but the slot stays held. Only `confirmDeleted` — a COMPLETED delete naming exactly that authenticator **and** a subsequent absence read — makes the passkey `revoked` and the enrollment **`removed`** (terminal), freeing the slot in the same transaction. Neon `activate` takes the same per-account `FOR UPDATE` lock, so activation vs. removal has one serialization order.
- **Blocked removals are retryable — with fresh bytes only.** A `revoking` target whose earlier attempt is `blocked`, with nothing `dispatch_in_flight`, may get a **new** attempt: fresh survivor WebAuthn over a fresh signed body (new timestamp), same authenticator id. The locked dispatch transaction refuses any body whose hash equals an earlier attempt's for that target — even one still inside the local freshness window — so a retry can never re-send old signed bytes (and an expired stamp is refused by the freshness check as before). Old attempts stay as history; the one-dispatch-per-target index still allows only one in flight; nothing is retried automatically; the target never returns to `active`. Works for formerly-active and pending-origin targets (the latter's enrollment stays `removal_in_progress` until a confirmation). A FAILED delete plus an absent target is still **not** a confirmation: if an earlier delete already succeeded, retries fail at Turnkey and the target stays `revoking` — a liveness dead end, not a false "removed". Slice S3 (below) adds the one, operator-only way out, and only on R2a evidence.
- **An uncertain CREATE is never harmless.** `blocked` is no longer terminal: it means "setup needs review — the create may have reached Turnkey". It holds the slot, is never abandonable, never re-authorizable, and re-checks are read-only discovery: exactly one byte-matching authenticator moves it to `turnkey_authenticator_created` (mapping persisted; then removable), anything else leaves it in review — a miss is never read as absence. `turnkey_enrollment_in_flight` likewise holds the slot and can't be abandoned. The passkey list's `walletAccess` (`none`/`uncertain`/`granted`) is never optimistic, and the UI says "Setup needs review — this passkey may already be able to approve payments" rather than "Setup in progress".
- **A dispatched CREATE is never proven absent by the server.** The browser still holds the exact signed body + stamp and can post it to Turnkey directly; clearing our copy doesn't prevent that, and Turnkey's own freshness / same-body rules are unverified (our local 2-minute window protects only *our* replay path, never Turnkey's public endpoint). So a FAILED/REJECTED activity plus a `getUsers` miss is **review** (`blocked`: slot held, not abandonable, no new CREATE, read-only discovery), never "safe to abandon or retry". There is no longer any path from a dispatched create back to `credential_registered`; a legacy `definitive_failure` row (written before this rule) is treated as uncertain authority and moved into review on its next re-check. At most **one** byte-identical replay is ever forwarded — `claimReplay` is a CAS on `turnkey_request_replayed` false → true, taken before the send — and create-activity recording is first-writer-wins (like removal's `recordActivity`). Recovery by an exact single match clears the stale review reason.

- **Schema** (`schema.sql`, hand-applied, idempotent): challenge purpose `backup_step_up`; enrollment states `removal_in_progress`/`removed` (discover-drop-add CHECK in a `DO` block); columns `registration_step_up_credential_id`, `registration_mint_id`, `turnkey_request_replayed`. The one-open index swap is **one guarded `DO` block = one transaction**: lock the table against writes, RAISE if any account already has more than one enrollment the new rule counts as open (e.g. `blocked` + another) — before anything changes — then create `backup_passkey_enrollments_one_open_per_account` (`state NOT IN ('active','abandoned','removed')`), and only then drop the Batch 2g index. ### Finite SafeOp Expiry + EntryPoint Nonce Reconciliation

A security slice on Real Pay. It does not change payment limits, the Safe owner, Turnkey signing, or Practice Mode.

- **Why `0` was a real exposure.**
  - Safe4337Module 0.3.0 passes the signature's `validAfter`/`validUntil` into `validationData` unchanged. EntryPoint v0.7's `_parseValidationData` maps `validUntil == 0` to `type(uint48).max` (verified against both upstream sources).
  - permissionless's `toSafeSmartAccount` defaults both values to `0`, so every SafeOp was signed never-expiring.
  - Every prepare gets its own nonce **key** at sequence 0 (viem's `nonceKeyManager`, a millisecond-timestamp key, verified in source and in all live rows). So a later payment never invalidates an earlier signed SafeOp.
  - Passkey removal doesn't help either: the SafeOp is signed by the Turnkey owner key, which survives it.
  - The only thing bounding a signed SafeOp was Pimlico's paymaster signature: `paymasterData` carries its own `validUntil`, observed at exactly prepare + 600 s. That is a third party's policy, never ours and never checked.
- **Window: 600 s from the chain's latest block timestamp at prepare; `validAfter = 0`** (`lib/real/payments/validity.ts`).
  - The EntryPoint enforces the intersection of the account's and paymaster's windows, so a longer window buys nothing for sponsored operations.
  - A shorter window would fail real passkey ceremonies. Observed prepare-to-confirm times ranged from 8 s to about 3 min.
  - The effective limit is unchanged, but it is now ours, enforced, and known to reconciliation.
  - `valid_until` and `prepare_block_number` are persisted on `payment_attempts`, both nullable.
- **Submit.**
  - The signature must carry exactly `validAfter = 0` and the stored `validUntil`. The preflight proves only that the owner signed *some* window, so the window is pinned separately.
  - With fewer than 60 s left, the server refuses to dispatch (`signed → failed`, nothing sent).
  - Clock skew is safe both ways: refusing early sends nothing, and a late send is rejected on-chain with AA22.
  - Rows without a window are never offered for signing and never dispatched.
- **Reconciliation without the bundler** (`lib/real/chain/entry-point.ts`). This runs only when the bundler has no receipt. It is read-only, never resends, and any error leaves the attempt as it is.
  - **Proven included:** this payment's own nonce lane has advanced **and** exactly one `UserOperationEvent` for its userOpHash and sender exists. The event's `success` decides between confirmed and failed.
    - The event search covers `[prepareBlock, prepareBlock + 600]`. That is a hard bound, because block timestamps strictly increase.
    - `sepolia.base.org` served a 601-block `getLogs` live.
  - **Proven never includable:** the finalized block's timestamp is past `validUntil` **and** `getNonce` evaluated at `blockTag: "finalized"` returns this exact nonce key at this exact sequence. The attempt then becomes `failed` with "no money moved".
    - `latest` state is never the proof of non-inclusion: a latest-state read and a finalized header are separate RPC observations that need not describe one coherent chain. Latest state is used only to discover inclusion (the matching event is that proof).
    - The state read uses the `finalized` block **tag**, never a numbered block, so no provider has to serve arbitrary historical state. Every `getNonce` value is decoded as `key << 64 | sequence` and its key must equal the requested key before its sequence is trusted; a wrong key, a `0n` for a non-zero key, or a malformed value is unresolved. A provider that rejects the `finalized` tag leaves the row unchanged.
    - The cost is roughly 22 min of finalization lag, measured live. It applies only to operations that never land.
  - **Never-dispatched rows** (`awaiting_authorization`/`signed`, e.g. a cancelled passkey prompt) past `validUntil` resolve through this same proof and nothing weaker. The server can't know the browser never signed, so "not submitted" is never read as "can't land". The update is a compare-and-swap from the row's own state, so a concurrent submit or cancel wins cleanly. Before this, an abandoned prepare held the account's one payment slot until the user cancelled it.
- **No new states.** The finite window only bounds the edge cases:
  - One residual trust assumption remains: a bundler rejection is still treated as final. The finite window now bounds even that case to 600 s.
  - Same-nonce replacement is not supported and not wanted.
  - No byte-for-byte resend is possible, because signatures are never persisted.

### Slice S1 — Real Pay Credential Attribution

A security slice on Real Pay. Before it, submit proved only that *some* owner signature was valid. Every passkey on the account authorizes the same Turnkey wallet key, so nothing recorded which passkey approved a payment. No change to the owner, the Safe, limits, the SafeOp window, nonce reconciliation, or Practice Mode.

- **Five different things, kept separate:**
  - **App session identity**: which active passkey the cookie was issued for. Checked on every request. It never authorizes a signature.
  - **Bound payment credential**: `payment_attempts.authorizing_credential_id`. `reserve()` sets it once, at prepare, to the session's own credential (re-checked active and owned). It is never client-supplied and never patched.
  - **Turnkey signing activity**: the `ACTIVITY_TYPE_SIGN_RAW_PAYLOAD_V2` the browser's pinned WebAuthn ceremony created. Its id is only a *locator* sent to `/submit`.
  - **Safe owner signature**: the ECDSA signature by the Turnkey wallet key over the SafeOp digest. It is identical in kind whichever passkey approved it.
  - **UserOperation inclusion**: on-chain. Reconciled exactly as before.
- **The prompt is pinned.** `/prepare` and `/latest` return the bound credential. `signPreparedPayment` refuses to sign without one and scopes the WebAuthn ceremony to exactly it (`allowCredentials`, decoded bytes). A browser holding only another passkey gets no approvable prompt. It is still one fresh ceremony per payment, with no reusable session and nothing stored in the browser.
- **The proof before dispatch** (`lib/real/server/payment-authorization.ts`). This mirrors Proof B. The server reads the activity back itself (parent key, read-only `getActivity` + `getUsers`) and requires all of the following:
  - It is the named activity, in the account's own child org, of type `SIGN_RAW_PAYLOAD_V2`, and `COMPLETED`.
  - Its intent signs **exactly this row's SafeOp digest** with the canonical owner (`HASH_FUNCTION_NO_OP`, hex). The server computes the digest from the durable fields, its own `validUntil`, and `validAfter = 0` (`computeExpectedSafeOpDigest`).
  - It has **exactly one** APPROVED vote, for this activity, by the account's Turnkey user. That vote's `publicKey` equals the `credential.publicKey` that `getUsers` maps to the bound credential. The mapping is matched by credential-id bytes, and by `turnkey_authenticator_id` when the registry has it. Primaries not yet backfilled are proven by bytes alone.
  - No *other* authenticator of that user shares that public key (normalized). If one does, the vote can't say which credential approved, and the proof is rejected.
  - Its signature result recovers the owner over that digest **and is byte-identical** to the owner signature inside the submitted Safe signature.
  - Together, these bind "approved by P" to "signed the digest of payment X". Neither half alone is accepted.
  - **Missing vs wrong.** Every check runs, and presence is read from the raw activity (not `summarizeActivity`'s `""` defaults).
    - **Rejected** if any field is *present and contradicts*: another org, type, digest, signer, encoding, or hash mode; FAILED or REJECTED; another user or activity on the vote; another vote key; more than one approval; readable votes with no approval; a shared or ambiguous key; a DB/Turnkey mapping conflict; malformed, non-recovering, or different signature bytes. This holds even if other fields are missing.
    - **Unavailable** if nothing contradicts but something needed is *absent or unreadable*: a failed read; a non-terminal status; missing org, type, intent, intent fields, `votes`, a vote entry, selection, or vote fields; the `result` object or `r`/`s`/`v`; the bound authenticator or its `credential.publicKey` (reported as `""`). An empty `votes: []` counts as missing proof, not proof of refusal, because a COMPLETED activity in a 1-of-1 org necessarily had an approval.
- **Submit ordering.** Structural checks come first. Then the session's credential must equal the binding by bytes. Otherwise the result is `wrong_passkey`: the row is not touched and nothing is re-bound, and the only way forward from another passkey is to cancel and start a new payment. Then comes the proof. Then the claim CAS `awaiting_authorization → signed`, which also writes the activity id (write-once) and `authorization_verified_at`. A loser of this claim re-reads and reports the row's *current* state. Then the existing expiry check, which now runs *after* the Turnkey reads, followed by the SafeOp preflight and the recomputed hash. Then the **atomic dispatch claim** `signed → submitting` (below), then dispatch. The durable pre-dispatch `submitting` rule is unchanged.
  - Proof outcome **"unavailable"** (read failed, not yet terminal, authenticator not visible) changes nothing and sends nothing, and returns `503 {retryable}`. The browser keeps the same signature and activity in memory, and "Continue" re-sends them with no second passkey prompt. The server's CAS still allows at most one dispatch.
  - Proof outcome **"rejected"** fails the attempt; nothing is sent.
  - A unique partial index (plus the in-memory equivalent) means one activity never authorizes two payments.
  - Legacy rows with no binding fail closed. They are never back-filled.
- **Revocation after signing — decided: no dispatch unless the approving passkey is still `active` at the moment the dispatch claim commits.**
  - The alternative was to honor an approval produced while the passkey was active, bounded by the 600 s window. It was rejected because a passkey leaving `active` (even `revoking`) already ends its app authority immediately, and the payment requires that passkey's own session anyway.
  - **The claim is atomic** (`PaymentAttemptStore.beginDispatch`). On Neon it is one transaction:
    1. Lock the account row: `real_accounts … FOR UPDATE`. This is the same first lock every 2g passkey transaction takes (removal dispatch, removal confirmation, enrollment activation) before touching `real_passkeys`, so the order can't deadlock against them.
    2. Run `UPDATE payment_attempts SET state='submitting' WHERE state='signed' AND EXISTS (bound passkey, same account, status='active')`. READ COMMITTED gives this statement a fresh snapshot after the lock.
    3. Commit. Only then is the bundler called; no network call happens while a lock is held.
  - A removal that commits first makes the claim fail (the attempt is marked failed; nothing is sent). A removal that starts later waits for the claim, and doesn't retroactively unsend it.
  - The in-memory adapter mirrors this with a synchronous check-and-write against the registry's passkey map.
  - Limit: this stops *our* dispatch only. The signed SafeOp stays valid on-chain until `validUntil` for anyone holding it, because the owner key is shared by every passkey and survives the removal.
- **Payment history.** Attribution is persisted (credential id + verified activity id + time) but not yet shown. `PaymentHistoryEntry` still carries neither. When it is shown, the plan is to join on the immutable credential id and display the passkey's *current* name. Names are presentation-only, and revoked passkeys keep their row and name, so no name snapshot is stored. Display names are never an authority identifier.
- **WebAuthn counters are not advanced by payments.** `getActivity`'s vote exposes `message`/`signature`/`scheme`, but whether these carry verifiable `authenticatorData` is undocumented and unverified. Counters therefore stay exactly as the last app login left them, and nothing is inferred. Verified counters would need the server to check the WebAuthn stamp itself (Model B-style stamp-and-forward), which is a larger change that is not taken.
- **Schema** (`schema.sql`, hand-applied, idempotent, all nullable): `authorizing_credential_id` (FK to `real_passkeys`, no `ON DELETE` action; passkeys are revoked by status, never deleted, so revoked ones remain as evidence), `turnkey_sign_activity_id` (unique where not null), `authorization_verified_at`.
- **Not proven by this slice:**
  - It does not stop anyone who controls *any* of the account's active passkeys from getting the wallet key to sign outside this app. Turnkey authority is per user, not per passkey.
  - The proof trusts Turnkey's own activity/vote records.
  - The bundler-rejection assumption is unchanged.
- **Verification status.**
  - Proven offline: the real client signing path against a stateful fake Turnkey, and independent one-field missing-vs-wrong fixtures. The guards were mutation-tested manually; every behavior-changing mutant was killed.
  - The shapes it relies on (`intent.signRawPayloadIntentV2.payload` echoing the 0x digest; `vote.publicKey` equal to `getUsers`' `credential.publicKey`) are the ones Proof B live-verified.
  - Neon DDL/uniqueness and the dispatch claim's lock serialization (a removal holding the account lock blocks a concurrent claim, which then refuses) are covered by `DATABASE_URL`-gated smoke cases.
  - **Live-verified** at the security closeout:
    - the primary P approved live Real Pay payments, and the backup S approved one — so a primary's vote key matches the same way (no longer a candidate);
    - the exact authorizing credential was attributed correctly for both P and S;
    - a submit from another passkey's session was refused with 409 (`wrong_passkey`);
    - the real account-lock serialization was proven;
    - each successful test payment produced exactly one UserOperation and one matching USDC transfer;
    - Turnkey and Safe authority state was unchanged afterwards.
  - Since S5 (L4), the lock serialization's READ COMMITTED requirement is pinned in code (see "S5" below).

### S2 — Real Pay Reconciliation + UX Hardening

A security/correctness closeout slice on Real Pay, following Slice S1. No change to credential attribution, the Safe owner, payment limits, or Practice Mode.

- **Finalized-state non-inclusion proof.** An intermediate S2 version inferred "unconsumed at finalized" from a `latest` nonce read plus a finalized header; an independent audit rejected that (two separate observations, not one coherent snapshot). The proof now reads the nonce at `blockTag: "finalized"` — still no numbered historical read — and validates the packed nonce key on every read (see the corrected bullet above).
- **The UI now reconciles itself, not just the server.** `resolvePaymentStatus`'s pre-dispatch expiry proof (`PRE_DISPATCH_EXPIRABLE_STATES`) already existed, but nothing client-side ever called `/status` for a resumed `awaiting_authorization`/`signed` row. `real-payment-store.ts` now checks immediately if the attempt is already past `validUntil` on load, or arms one timer for `validUntil + 1 s`. Because Base finality lags `validUntil` by ~20 min, that first answer is normally still non-terminal, so the store follows up every `EXPIRY_FOLLOW_UP_MS` (75 s) until the attempt is terminal, replaced, or the generation changes (reset/account switch). At most one timer is outstanding; every arm clears the previous one, and the callback re-checks generation + attempt id. Presentation is derived from the attempt's own `validUntil` via the store's `isAttemptPastValidity` (never `Date.now()` in render), not a new payment status. Pre-proof copy is neutral ("This payment's approval window expired. We're waiting for final confirmation before showing the final result."); only the server's terminal failure says "No money moved".
- **Resume-screen UX against a stolen session cookie.** A stolen app session cookie can prepare a payment but cannot authorize it (Slice S1's binding). The residual risk is social engineering: the legitimate user later approving something they didn't start. The resume screen now shows the full recipient address (not only a 4+4 shortened form) and an explicit "Only continue if you started this payment" warning.
- **Cancel response correctness.** The client's `cancel()` used to ignore the response status entirely, showing a false "cancelled" state even on a 409 (a concurrent submit already won). It now checks `response.ok`; on a non-2xx it re-fetches and adopts the real durable state; on a network-level failure (no response at all) it preserves the existing attempt/status rather than guessing in either direction.
- **No response crosses a generation.** `checkStatus`, `cancel` (both its own response and its status re-fetch), and the expiry timer capture the store generation and attempt id before awaiting and discard the result entirely if either changed — an in-flight request for account A can never overwrite account B's attempt, status, clock offset, or error.
- **Dismissing the passkey prompt keeps the pending payment.** A WebAuthn cancellation signs nothing, but the durable row is still `awaiting_authorization` and still holds the one active-payment slot. The UI now stays on that payment's resume screen (amount, full recipient, warning, Continue, Cancel payment) instead of returning to review/Edit, which implied nothing was pending. Only a successful cancel (2xx) shows the compose form again.
- **Reduced browser-clock dependence.** `/prepare`, `/latest`, and `/status` now return `serverNowSeconds` — the server's own wall clock, the same one `resolveSubmitPayment`'s dispatch-margin check is judged against (deliberately not the chain's clock). The client derives an advisory `clockOffsetSeconds` from it and uses `local Date.now() + offset` for `client-sign.ts`'s pre-signing validity gate, so a skewed local clock can't falsely refuse (or falsely accept) a payment. The server remains independently authoritative at `/submit`; this closes a client-side false-negative, not a trust boundary.
- **Stale `failure_reason` on confirmation.** The Neon `payment_attempts.transition()` used `COALESCE(patch.failureReason, failure_reason)`, which cannot distinguish "explicitly clear it" from "leave it alone" (both are SQL `NULL`), so a row that resolved from e.g. `unknown` (with a failure reason set) to `confirmed` kept the stale reason. Fixed with the same `has()`-guarded `CASE WHEN` pattern `passkey_revocation_attempts.transition` already used; `resolvePaymentStatus`/`reconcileAgainstEntryPoint` now pass `failureReason: null` explicitly on every transition into `confirmed`. The in-memory store already handled this correctly. A `DATABASE_URL`-gated Neon smoke case (`neon-smoke.test.ts`, "S2: an explicit failureReason: null clears…") covers the adapter. It was exercised live as part of the full Neon smoke suite, which passed 44/44 during the S5 verification.
- **Legacy rows (no `valid_until`/`prepare_block_number`) — re-audited, no change needed.** Never offered for signing (`toPublicAttempt`'s `hasPreparedFields`), never declared expired by the new proof (`reconcileAgainstEntryPoint` and the pre-dispatch branch both return early on a null `validUntil`), still cancellable, still reconcile-only once submitting. The client's own expiry-scheduling function has the same guard.
- **Residual, accepted (not closed by this slice):** a signature produced in a compromised browser, once cancellation or expiry resolves our own row, can no longer be dispatched *through this app* — the CAS on `signed → submitting` and on cancel both check the row's live state — but the signature itself remains a valid bearer credential for that SafeOp **directly against the bundler/EntryPoint** until `validUntil` (max 600 s), because the owner key is shared by every passkey and Safe4337's on-chain validity window isn't something our server can revoke. Bounded and time-limited; not eliminated.
- **`eth_sendUserOperation` never retried by us or by viem.** Verified against the installed `viem@2.56.8`/`permissionless@0.3.7`: `client.sendUserOperation` (via `bundlerActions`) is viem's own action, which pins `retryCount: 0` as a per-call override — confirmed to win over the transport's own default. No code change; pinned by a regression test (`test/lib/real/pimlico-send-retry.test.ts`) against the library behavior itself.
- **Live-verified** at the security closeout:
  - finalized-tag reconciliation ran live: the finalized block's timestamp was past `validUntil`, the prepared nonce key and sequence were unchanged, and the attempt was terminalized only after that finalized proof;
  - the expiry liveness and follow-up checks ran after `validUntil`;
  - a normal $0.01 payment produced exactly one UserOperation and one USDC transfer;
  - a safe cancel produced no Turnkey activity, no UserOperation, and no USDC transfer;
  - the Safe, its owners and threshold, and the passkeys were unchanged afterwards.

  Offline proof, unchanged: fake RPC fixtures with independent latest/finalized nonce state, packed-key and malformed-value injection, and numbered-read/finalized-tag failure injection; store/component tests with fake timers; the key guards mutation-tested.
- **Retained residual — `finalized`-tag dependency.** The configured RPC served `eth_call` at the `finalized` tag in the live run. If a future provider doesn't, expiry proofs never succeed (fail closed): an expired pre-dispatch attempt then frees the slot only when the user cancels it, and a `submitting`/`unknown` row stays reconcile-only.
- **S5 (M1):** every EntryPoint reconciliation now first requires the RPC to report Base Sepolia's chain id (see "S5" below).

### Slice S3 — Blocked Passkey-Removal Operator Recovery

A liveness slice on 2g-H removal. A `blocked` removal has no exit of its own. If the target authenticator is already gone at Turnkey (e.g. the DELETE landed but its response was lost), every user-authorized retry fails there and blocks again. The target stays `revoking` forever, and a pending-origin target's enrollment holds the one-open-enrollment slot forever. S3 adds exactly one way out: an **operator-only** resolver that terminalizes such a row when Turnkey's read-only ledger independently proves it against this app's own durable DELETE history. No change to Turnkey authority, WebAuthn, the owner, the Safe, Real Pay, or Practice Mode.

- **Not a wallet-authority path.** `lib/real/server/passkey-revocation-resolver.ts` holds only a four-method read-only port (`getActivities`, `getActivity`, `getUsers`, `getAuthenticators`). It has no `fetch`, never forwards a signed request, sends no Turnkey mutation, signs nothing, and never touches an `active`/`pending` passkey, the owner, or the Safe. It only records locally a deletion Turnkey already performed. It is not wired into `runtime.ts`, any route, or any browser code (a boundary test enforces this). It runs only through the env-gated admin runner `test/admin/resolve-passkey-revocation.admin.test.ts`:
  - exactly one `REAL_ADMIN_APP_USER_ID` and one `REAL_ADMIN_REVOCATION_ATTEMPT_ID` per run;
  - **dry run by default**; the database is written only with `REAL_ADMIN_RESOLVE_COMMIT=1`, and the commit run redoes every read itself;
  - no force/skip/mark-revoked flag, no credential-id-only mode, no sweep.
- **Evidence (R2a only).** All of the following must hold, or nothing changes:
  1. **Local state.** The attempt is `blocked` and is the newest non-cancelled attempt for its target: any newer `authorization_needed`/`blocked`/`dispatch_in_flight`/`confirmed` attempt refuses. Nothing is in flight. The target is `revoking` with its mapping unchanged. Another active mapped passkey exists. Any enrollment for the target is `removal_in_progress` or `active`.
  2. **Receipt.** A COMPLETED `DELETE_AUTHENTICATORS` in exactly this org and of exactly this type, whose intent is `{userId: account user, authenticatorIds: [target]}` and whose result is `[target]`. Its `fingerprint` must equal `"sha256:" + sha256` of a DELETE body **this app stored** for the same account, target credential and target authenticator id. The stored body is strictly re-parsed and re-hashed over its exact bytes. Exactly one activity may match, and no stored body may map to more than one activity. The receipt is re-read by id and must be identical on id, org, type, status, fingerprint, createdAt, intent and result. **R2b — a dashboard/external delete with no stored body — is never accepted.**
  3. **No later re-grant of authority.** Nothing at or after the receipt's server `createdAt` can have restored the target's authority. Same-second counts as "after", because the live API reports whole seconds. Activities of every status count, since a pending create may still complete.
     - The parsers are explicit: one for each `v1Intent` member that, per `@turnkey/http` 6.5.0's schema, transitively carries `v1AuthenticatorParams`/`V2`. That is CREATE_AUTHENTICATORS(\_V2), CREATE_USERS(\_V2–V4), ACCEPT_INVITATION(\_V2), RECOVER_USER, CREATE_ORGANIZATION(\_V2) and CREATE_SUB_ORGANIZATION(\_V2–V8).
     - Refusal: any of them naming the target's credential bytes or authenticator id. Also refused: any that is unparseable, and any unknown intent carrying an `attestation`/`authenticator(s)` field.
     - API keys, sessions and OTP/OAuth/email auth register no WebAuthn credential, so they can't restore this credential's authority.
  4. **Absence, twice.** Two full snapshots, the second taken immediately before the commit phase. Each must show all of:
     - `getUsers` (all users) and `getAuthenticators` (the account user) agree exactly;
     - the target's id and credential bytes appear under **no** user;
     - every non-revoked, non-target mapped passkey (including `revoking` ones) appears exactly once with exact bytes;
     - no duplicate ids or bytes, and no unexplained authenticator on the account user.

     Any error, `null`, malformed or partial read fails closed. No fixed sleep is a safety predicate. Absence alone is never enough.
  5. **Freshness.** A final read of the activity-log head must equal the head from the full walk; otherwise the resolver refuses and a rerun is required. This only narrows the read→commit window; it is not a linearizability claim.
- **The walk.**
  - Pages of 100, newest first, older pages via `after` = last id, **until an empty page**. A short page is never taken as the end.
  - A page cap, a repeated id, a stalled cursor, an over-full page, a foreign-org row, a malformed row, or `createdAt` increasing while walking back ⇒ `turnkey_read_incomplete`. A read error ⇒ `turnkey_read_failed`. No partial walk ever resolves.
- **The commit** (`passkey-revocation-resolution-store.ts`) is one dedicated, account-locked batch and never calls `confirmDeleted` (that would overwrite the activity status). No Turnkey call happens while the lock is held.
  - `SELECT … FROM real_accounts … FOR UPDATE` **first**, the same boundary as `beginDispatch`/`confirmDeleted`/`activate`.
  - Then a CAS `blocked → confirmed` that touches **only** `state`/`updated_at`. It re-checks every local fact above inside the lock: exact attempt and target, no in-flight or newer non-cancelled attempt by `(created_at, id)`, an active mapped survivor, the enrollment compatible, and the receipt-body attempt still present with `sha256(convert_to(body,'UTF8'))` equal to the hash. Its own `turnkey_activity_id`/`turnkey_activity_status`/`failure_reason` must equal what the resolver read.
  - Then target `revoking → revoked`, the enrollment `removal_in_progress → removed` (the only point the slot frees), survivor promotion exactly as `confirmDeleted`, and one audit row. Every statement after the CAS is bound to it by `state = 'confirmed' AND updated_at = now()`, so a lost claim writes nothing.
  - Guards roll back the whole batch if any of these fails: `confirmDeleted`'s three; at least one active passkey remains; the audit row exists; the attempt's own fields are unchanged; the receipt body is still exact.
- **Audit — `passkey_revocation_resolutions`** (hand-applied, append-only by construction). The recovery receipt lives **only** here, never on the attempt.
  - Identity: `revocation_attempt_id` UNIQUE, account, target credential and authenticator id, the original failure reason.
  - Receipt: activity id (UNIQUE), `receipt_source` (`own_attempt` only when the receipt is the attempt's own recorded activity, otherwise `stored_attempt_body`), the body attempt id and body **hash**, the receipt's Turnkey createdAt.
  - Observation: activity-log head, both absence timestamps, the observed survivor authenticator ids, resolver version.
  - `receipt_activity_id` is UNIQUE because a receipt names exactly one authenticator id, which maps to at most one passkey, and a resolved target is `revoked`. So one receipt can truthfully resolve at most one attempt.
  - No body, stamp, assertion, key, or operator identity is stored.

### Slice S4 — Session / Account Security Hygiene

A hardening slice on the app session and the `/api/real/**` request surface. No change to payment signing, Safe ownership, Turnkey authority, the S3 resolver, or Practice Mode.

- **Account session epoch (server-side revocation).** `real_accounts.session_epoch BIGINT NOT NULL DEFAULT 0`. Every session token carries the epoch it was minted at; `readAuthenticatedRealAccount` requires, in order: a valid HMAC, the current token version, an unexpired `exp`, an existing, `active` credential owned by the token's `appUserId`, an existing account, and `token.sessionEpoch === account.sessionEpoch` (exact equality). Login and registration mint at the account's current epoch and never change it, so signing in on one device never signs out another. No per-session table and no denylist.
- **"Sign out everywhere."** The only sign-out, and account-wide: `DELETE /api/real/session` authenticates the current session, increments the epoch in one `UPDATE … SET session_epoch = session_epoch + 1` (unconditional: a concurrent increment only raises it further), and only then clears this browser's cookie. After the increment every previously issued session for the account is dead server-side, even if the cookie clear never reaches the browser. If the increment fails, the cookie is left alone and the caller gets a 500, never a false success. A request without a valid session gets a 401. The UI button says "Sign out everywhere", with a line saying it covers every device.
- **Token v2, forced re-login.** The session payload is `{ v: 2, appUserId, credentialId, exp, sid, sessionEpoch }`. A v1 token has no epoch and is refused by version. There is no legacy fallback, so every pre-S4 session signs in again once. Parsing accepts exactly `<base64url payload>.<43-char base64url MAC>` (extra or empty segments, padding, and stray characters are refused before the MAC is computed); the MAC compare stays `timingSafeEqual`.
- **Session secret format policy.** `REAL_SESSION_SECRET` is still used verbatim (its UTF-8 bytes) as the HMAC key, but config now fails closed unless the value is an *encoding* that decodes to ≥ 32 bytes (`decodeSessionSecret`, `lib/real/server/session.ts`):
  - **Hex:** hex digits only, even length, so at least 64 characters. A string made only of hex digits is judged as hex and never re-read as base64 (63 hex characters would otherwise decode as 47 bytes of base64).
  - **Base64 or base64url:** one alphabet (never mixed), padding optional but correct if present, never a `4n + 1` length, and canonical: re-encoding the decoded bytes must reproduce the input, which rejects non-zero trailing bits that Node's lenient decoder would silently drop.
  - **Anything else is refused:** passphrases and raw text of any length (e.g. `correct horse battery staple!!!!`, eight 🔒 emoji). There is no byte-length fallback.

  `openssl rand -hex 32` passes, as does the existing 64-hex local secret. The error names the variable, never the value. This is a format policy, not an entropy measurement: a hand-typed string that happens to be a canonical encoding still passes. Cookie attributes are unchanged: `HttpOnly`, `SameSite=Lax`, `Path=/`, no `Domain`, `Secure` in production, 7-day `exp`. The `__Host-` prefix is deferred until production host/cookie details are settled.
- **Origin gate (`proxy.ts` → `lib/real/server/request-gate.ts`).** One Next 16 proxy (Node.js runtime) matched to `/api/real/:path*`, so the two cookie-issuing routes (`register/verify`, `login/verify`) and every authenticated mutation are covered without per-route code. Safe methods (`GET`/`HEAD`/`OPTIONS`) pass. For every other method:
  - `Sec-Fetch-Site: cross-site` → 403.
  - An `Origin` header, when present, must exactly equal one of `NEXT_PUBLIC_REAL_ORIGIN`'s origins (the same list WebAuthn verifies against), so same-site-but-cross-origin callers and `Origin: null` get 403; with no origins configured, any `Origin` is refused.
  - **No `Origin` header is allowed through, deliberately:** browsers attach `Origin` to every non-`GET`/`HEAD` request, so only non-browser callers (server tools, tests) omit it, and they carry no victim's cookie. They still face the Fetch Metadata rule, the content-type rule, and each route's own auth.
  - `Content-Type` must be `application/json` (parameters allowed) → otherwise 415, which is what keeps the CORS-"simple" `text/plain`/form shapes away from JSON-parsing routes. The exemption is an explicit list of the six body-less routes (`register/options`, `login/options`, `backup/step-up/options`, `[credentialId]/revoke/options`, `payments/[id]/cancel`, `DELETE session`), checked against the real client calls. A new route is JSON-only by default.
  - No CSRF tokens. With Real Mode disabled the gate steps aside (every route already 404s).
- **Challenge cleanup.** `ChallengeStore.create` purges `webauthn_challenges` rows with `expires_at` before now in the same statement as the insert (`WITH purged AS (DELETE …) INSERT …`, a range scan on `webauthn_challenges_expires_at_idx`). The cutoff uses the server clock that wrote `expires_at` and that `consume` checks, so nothing still consumable is purged. No scheduled job, no schema change; challenge entropy, single-use `DELETE … RETURNING`, purpose binding, and TTLs are unchanged.
- **Static headers.** `next.config.ts` sets `Content-Security-Policy: frame-ancestors 'none'`, `X-Frame-Options: DENY`, and `X-Content-Type-Options: nosniff` on every path. Nothing else: no script/style CSP and no HSTS (left to the hosting layer until production deployment is verified).
- **Client state hygiene.**
  - Sign-out shows the signed-out screen only after the server confirms. On a 500 or network error the account stays, with an error. On a 401, this browser is shown signed out, with a note that other devices were *not* signed out from here.
  - `real-account-store` now has the same generation guard as the balance/history/payment stores: a late session-check, login, or sign-out answer can't overwrite a newer transition.
  - `real-passkeys-store` gains `reset()` and `bindAccount(appUserId)`. Switching accounts (or signing out) bumps its generation; every action captures it, applies nothing once it is stale, and stops before its next server call, so a half-finished setup or removal for account A never continues under B's cookie. Rebinding the same account is a no-op, so remounting mid-flow is safe. List loads are also latest-wins within one account.
  - `GET /api/real/session` clears a cookie that no longer grants access (legacy, expired, revoked credential, old epoch, tampered). A registry error is a 500 and clears nothing.
- **Offline proof.** Unit and route tests against the actual `route.ts` code:

A local `next start` smoke returned 403/403/415/403 for foreign-origin, cross-site, `text/plain`, and foreign-origin `DELETE` requests, and the three headers on pages and API responses.

### S5 — Final Security Audit + Freeze

A read-only, repo-wide audit of the integrated Real Mode system (onboarding, sessions, backup/removal/recovery, Pay, reconciliation, Safe/owner, Neon, admin tooling, browser, configuration) at `23450e0`. Result: **no Critical or High findings**, three Medium, several Low. This pass fixes M1 and L4, records every other finding below, and reconciles the docs. No change to Turnkey authority, the owner, the Safe, payment limits, session semantics, or Practice Mode.

- **M1 — wrong-chain reconciliation (fixed).** The canonical EntryPoint v0.7 exists at the same address on most chains, and wherever this Safe never used a given nonce key, `getNonce` returns exactly `key << 64 | 0`. So an RPC URL pointing at the wrong chain could satisfy the finalized non-inclusion proof and mark a payment that landed on Base Sepolia `failed` with "No money moved", freeing the slot for a second payment. Prepare was already safe (`readCashBalance` checks the chain id); reconciliation was not. `readUserOperationChainState` (`lib/real/chain/entry-point.ts`) now first calls `getChainId()` and returns `unresolved` — before reading anything else — unless it is exactly `84532`; a failed chain-id read is also `unresolved`. Wrong-chain evidence can no longer produce `included`, `expired_unincluded`, or any terminal write. Tests reuse each proof's exact fixture state on a wrong chain and with a failing chain-id read, through both the chain function and `resolvePaymentStatus` (rows unchanged, slot still held); the guard and its catch were mutation-tested.
- **L4 — Neon isolation (fixed).** Every lock-then-read transaction (payment and removal `beginDispatch`, `confirmDeleted`, `activate`, the S3 resolution commit) needs the statement after `SELECT … FOR UPDATE` to take a fresh READ COMMITTED snapshot. Under a REPEATABLE READ database default, payment `beginDispatch` would read a just-revoked passkey as still active. All production Neon clients are now built by `createNeonSqlClient` (`lib/real/server/neon-store.ts`) as `neon(url, { isolationLevel: "ReadCommitted" })`, which is the runtime stores, the S3 admin runner, and the gated smoke suite. Checked against the installed `@neondatabase/serverless` 1.1.0 source and types: the option is the client default for `sql.transaction()` batches (sent as `Neon-Batch-Isolation-Level`); a per-call value still overrides it, so the S3 snapshot read keeps its read-only REPEATABLE READ; single statements carry no isolation. Tests drive the real driver with `fetch` intercepted and assert the header each locking transaction sends; removing or changing the pin fails them.
- **Live-verified (read-only against Base Sepolia, Turnkey, and real Neon; the only writes were the smoke suite's own scratch rows).**
  - **M1.** The configured RPC reported chain id 84532, and the production `readUserOperationChainState` returned `included` for a known confirmed payment, with a transaction hash matching the stored one. Temporary wrong-chain probes (chain ids 8453 and 11155111) returned `unresolved`, and instrumentation showed they stopped after `getChainId`: no block, nonce, log, or finalized read. A counterfactual run on the same wrong-chain data with the guard bypassed returned `expired_unincluded`, so the exposure was real. No payment row changed.
  - **L4.** The full `DATABASE_URL`-gated Neon smoke suite passed 44/44 through `createNeonSqlClient`. A live probe showed pinned batches running at READ COMMITTED and the S3 snapshot read still REPEATABLE READ and read-only. The database default currently reports READ COMMITTED, so the pin guards against a future change rather than altering today's behavior. Zero scratch residue remained.
  - **Invariants,** compared between a snapshot before and one after: Neon Real-data snapshots, P/S/D and the S3 recovery state, Turnkey activity and authenticator state, and the Safe's configuration were all unchanged, and no chain write occurred.

**Before any Turnkey dashboard / account recovery / migration work begins**, its first security tasks are these two (deliberately not done in S5). **Both are done and live-verified, and L2's identity indexes are applied.** The next security prerequisite, before any operator Turnkey-create recovery resolver: exact CREATE dispatch evidence (below).

- **L2 — registration identity hardening (implemented, live-verified; indexes applied).** The gap: discovery bound a sub-org by credential id alone (an id whoever registers chooses) and took the first user; `real_accounts` had no uniqueness on sub-org / owner / Safe; and registration's pre-checks used the client's `response.id` while the durable id came from the attestation. A Turnkey authenticator unknown to the database (e.g. one added through the dashboard) could let a registration alias another account's sub-org and Safe. There was no money path (the attacker's key isn't a Turnkey authenticator), but the identity invariant broke.
  - **Credential-id binding** (`registration.ts`). WebAuthn verification runs first. `response.id` must then equal the attested `registrationInfo.credential.id` by decoded bytes (`credentialIdsEqual`; `@simplewebauthn/server` 14 only checks `id === rawId`). A mismatch is the fixed "Registration could not be verified." 400: no attempt, no Turnkey call. Every pre-check (any existing passkey, any role or status; any attempt) uses the attested id.
  - **Automatic uncertain-create rediscovery is DISABLED (Option 3, after independent audit H1).** Discovery (and a stricter version: exact credential-id bytes + exact COSE key + one user/authenticator/wallet account + no API keys/OAuth) proves only that a sub-org *contains* the credential. It cannot prove that **our own** `CREATE_SUB_ORGANIZATION` for **this** attempt made it, or that no other authority exists in it: an imported or exported wallet, enabled email/SMS/OTP/recovery features, policies, private keys, root-quorum or user changes, or anything done out of band since. So an attempt whose create response was lost stays `provisioning_in_flight` / `unknown` and reports `PROVISIONING_NEEDS_REVIEW_REASON` ("needs review … trying again won't resolve it"). It makes **no Turnkey call** of any kind, does no adoption, writes no account/passkey, and issues no session. `discoverAccountByCredentialId` and its candidate evaluation were **deleted**; `turnkey-discovery.ts` now exports only the shared read/compare helpers (S1, 2g, S3, backfill). Fresh provisioning is unchanged: Turnkey's own successful response → `turnkey_created` → finalize → `active`.
  - **Future recovery = an operator-only provenance resolver (not built).** Its prerequisite, **exact dispatch evidence** (the exact request body persisted before dispatch, and the activity id recorded when one becomes observable and its persistence succeeds), is now captured — see "Provisioning Evidence Capture" below. Attempts dispatched before that slice have no such evidence, and provenance can never be proven for them. The resolver must then prove, read-only:
    - a single completed parent `CREATE_SUB_ORGANIZATION_V8` whose fingerprint and intent match our stored body and whose result names the sub-org;
    - unchanged current child authority (users, keys, OAuth, email/phone, features, quorum, policies, wallets `imported`/`exported`, private keys);
    - an empty child activity history (S3-style complete walk).
  - **Research for that resolver, not a current mechanism (read-only, live):** production discovery against the live `CREATE_SUB_ORGANIZATION` primary found exactly one exact candidate; `list_users` returns `apiKeys` and `oauthProviders` as present `[]` arrays for both existing users; the child history holds no creation activity; the V8 result names only the sub-org, root user ids, and wallet id/addresses. Still unverified: parent-org authority inside children, activity-history completeness and retention, `disable*` flags' representation in `features`, and whether `EXPORT_WALLET_ACCOUNT` sets `wallet.exported`. (The fingerprint rule for parent-API-key requests has since been observed live — see "Provisioning Evidence Capture".)
  - **Exact key comparison** (`strictCanonicalTurnkeyPublicKeyBytes` / `turnkeyPublicKeysEqual`). Live-confirmed format: Turnkey's `credential.publicKey` is canonical unpadded base64url of the raw COSE_Key. For a P-256 primary (`CREATE_SUB_ORGANIZATION`) and backups (`CREATE_AUTHENTICATORS_V2`) it is 103 characters and 77 bytes, byte-identical to our stored key. Accepted spelling: a string, base64url alphabet only, no padding or whitespace, and decode → re-encode must reproduce it. Anything else matches nothing. This replaces the trimming, case-folding `normalizeTurnkeyPublicKey` in S1 attribution and 2g Proof B; a malformed bound key in S1 is now rejected. **Live-verified (read-only): the activity `vote.publicKey` uses the same representation.** 7 specifically attributed activities (4 S1, 3 Proof B) plus all 11 approved signing votes in both accounts' histories were checked. Every vote key was canonical unpadded base64url, equal as a raw string and as decoded bytes to the expected authenticator's key, and never a case-only variant. That holds for both `CREATE_SUB_ORGANIZATION` and `CREATE_AUTHENTICATORS_V2` authenticators.
  - **Identity conflicts → `blocked`** (new exit `turnkey_created → blocked`, reason `REGISTRATION_IDENTITY_CONFLICT_REASON`). If another account holds the attempt's sub-org or owner, or the Safe about to be written (`pg_catalog.lower(...)`, schema-qualified exactly as the indexes compare, so no search_path can substitute another function), finalize blocks the attempt and writes no rows. Neon: an UPDATE after the row lock, before the CAS, in the same transaction. A concurrent conflict that statement couldn't see surfaces as a 23505 naming exactly one of the three identity indexes (the `constraint` field, or the message's quoted name; nothing else is relabeled), and a follow-up `[lock, block]` transaction blocks the attempt. The account insert is now `ON CONFLICT (app_user_id) DO NOTHING`, so identity collisions raise instead of being swallowed. In-memory: the same pre-claim check, and the registry throws `IdentityConflictError` (the indexes' twin), which finalize turns into `blocked`. No automatic recovery from `blocked` (no operator tooling yet). Two concurrent finalizes claiming the same identity for different attempts are serialized only by the identity indexes; the pre-claim check alone can't close that window.
  - **Safe-owner binding** (L3 audit Low 1). Onboarding passes the owner it derived the Safe from (`safeOwnerAddress`). The CAS wins only if the locked attempt's owner still equals it (`pg_catalog.lower(...)` / `addressesEqual`), otherwise no rows and pending. No network call runs inside the transaction.
  - **`active` is finalize-only** (L3 audit Low 2). Both adapters' `transition()` throws for any move to or from `active`. Production never used either (onboarding's four transitions were audited). The in-memory compensation now restores on state rather than object identity, so a concurrent counter update can't leave an active attempt without rows.
  - **Migration (applied).** Identity uniqueness is enforced by three case-insensitive unique indexes on `public.real_accounts`: `lower(sub_organization_id)`, `lower(owner_address)`, `lower(safe_address)`. They come from `schema.sql`'s "S5 L2 identity-index migration", one DO block that does the same on every run (never skipped because the names exist):
    1. Lock `public.real_accounts` (`SHARE ROW EXCLUSIVE`).
    2. Re-check duplicates per `lower(...)` identity inside the lock (RAISE; nothing chosen or merged).
    3. `CREATE UNIQUE INDEX IF NOT EXISTS real_accounts_{sub_organization_id,owner_address,safe_address}_lower_key … (pg_catalog.lower(col))`.
    4. **Validate all three from the catalog**, since IF NOT EXISTS trusts only the name. Each must be an index in the target schema, on that table, btree, UNIQUE, VALID, READY, immediate, not exclusion, not partial, with exactly one key that is an expression deparsing to exactly `lower(<col>)` over a `pg_catalog.text` column, depending on exactly that one column **and nothing else**, with the default operator class and a deterministic collation.

    **Which `lower()` (audit M1).** The block's first statement pins `search_path` to `pg_catalog, pg_temp` for its own transaction (`set_config(..., true)`), and every DECLAREd type is schema-qualified (declarations resolve before that pin). It then requires `pg_catalog.lower(pg_catalog.text)` to be a built-in (OID < 16384) that unqualified `lower(text)` resolves to. Under the pinned path Postgres deparses an index expression as unqualified `lower(col)` **only** if it calls exactly that function (functions are never looked up in `pg_temp`, and only superusers can add to `pg_catalog`); a look-alike prints schema-qualified and fails. Independently, Postgres never records dependencies on built-in (pinned) objects but always records them on a user-defined function, type, collation, or opclass. So any such dependency refuses the index. No `pg_depend` edge to the built-in is assumed, and the internal expression tree is never parsed.

    A wrong same-named object (a table, or a non-unique / raw-column / wrong-column / other-table / partial / multi-key / invalid index) RAISEs and rolls the whole block back. It is never dropped or repaired. The schema is one `target_schema` constant. Offline checks are static (every required predicate is pinned). The gated `l2-identity-migration.smoke.test.ts` (`REAL_SMOKE_L2_MIGRATION=1`) runs the exact block against throwaway scratch schemas for each wrong-definition case, the duplicate cases, clean creation, and the rerun. It adds two shadow-`lower` cases: a same-named UNIQUE index on an IMMUTABLE look-alike `lower(text)` (which provably deparses as plain `lower(owner_address)` under a hostile `search_path`) must be refused and left untouched. A clean run under that hostile path must build built-in indexes that reject case-only duplicates. The gated Neon smoke adds pre-index L2 cases and `REAL_SMOKE_L2_INDEXES=1` post-index cases. The gated `l2-identity-race.smoke.test.ts` (also `REAL_SMOKE_L2_INDEXES=1`) holds an uncommitted colliding holder in an interactive WebSocket transaction. It waits until `pg_blocking_pids` shows production `finalize` blocked on it, then commits, and requires the real 23505 naming each identity index, a whole rollback, exactly one follow-up block, and zero loser rows. A ROLLBACK variant lets finalize complete.

### Provisioning Evidence Capture

The prerequisite S5 L2 named for any future Turnkey-create recovery. It **captures evidence; it recovers nothing**. Option 3 is unchanged: an uncertain `CREATE_SUB_ORGANIZATION` is never discovered, adopted, retried, or resumed, and a `provisioning_in_flight` attempt still reports needs-review with **zero** Turnkey calls. No change to Turnkey authority, the owner, the Safe, WebAuthn, sessions, Real Pay, finalize (L3), the identity indexes (L2), or Practice Mode.

**Status: COMPLETE / CLOSED — evidence capture only.** Implemented; offline-verified including the independent-audit remediation (M1, L1–L6); the migration is live-verified on a disposable Neon branch and applied to the real Neon database; and one controlled live registration (localhost, real Neon + Turnkey testnet) then exercised the raw Turnkey create transport and the whole evidence path end to end (details under "Live verification"). **Closing this slice does NOT mean** that an uncertain-create recovery or operator resolver exists (not built), that adoption exists (it does not; automatic adoption stays disabled), that same-body resubmission exists (a future resolver primitive only — never implemented, never exercised), or that the public-deployment prerequisites are complete (they are not; see the end of "Live verification"). The dispatch table exists in the real database's `public` schema, so the claim-plus-evidence statement runs there. Any other environment must apply the schema block **before** deploying this code: the claim is one statement with the evidence INSERT, so without the table every new registration fails closed (the attempt stays `verified`).

- **What was wrong before.** The create went through `createActivityPoller(client.createSubOrganization)`. The SDK serialized and stamped the body internally, so the exact bytes were never visible; it kept the activity id in a closure that any later error discarded; it polled with no bound; and nothing per-dispatch was stored, not even the activity id of a successful create.
- **The exact-body-before-dispatch invariant** (`lib/real/server/provisioning-dispatch.ts`). In order:
  1. Read the clock **once**. `buildCreateSubOrganizationBody` (pure; evidence version 1) builds the one request string. That timestamp is both `timestampMs` and the name suffix. No nonce was added: the name already carries the per-attempt `appUserId`.
  2. Compute our SHA-256 of its exact UTF-8 bytes.
  3. `beginProvisioningDispatch` commits the `verified → provisioning_in_flight` claim **and** the evidence row together. A lost claim inserts nothing and sends nothing. If that transaction fails (e.g. a constraint), it rolls back and the attempt stays `verified`. If it committed but its response was lost, the call throws with the claim and evidence durable and nothing sent: review, fail closed.
  4. Take the body **returned by the store**. It must equal the built string, and its digest is recomputed. Otherwise nothing is stamped or sent.
  5. Stamp that persisted string and POST exactly that string, once. The stamp is never stored or returned.
  6. When an activity id becomes observable (Turnkey's answer carries one, even on a non-2xx), record it (write-once) **before** any poll or follow-up read. Only this database write may be retried, once; the create is never re-sent. The id is on the row only if that write succeeded. If the submit times out, fails in transport, or returns an unreadable answer, no id is ever observed, and the row holds only the exact persisted request body and its digest (the case an operator can later investigate only by that evidence).
  7. If the status is `CREATED`/`PENDING`, poll that exact id under one deadline. Record the terminal observation (write-once).
  8. Compare the activity with the evidence (below). A definitive `FAILED`/`REJECTED` → `revertProvisioningAfterDefinitiveFailure`; a validated `COMPLETED` → the bound wallet-account read, then `advanceProvisioningToTurnkeyCreated`, then the unchanged Safe/finalize path. Everything else is review.
- **`provisioning_in_flight` is claim-only** (like `active` is finalize-only). The generic `transition()` refuses to enter or leave it. The only way in is `beginProvisioningDispatch`; the only ways out are two single-statement CASes, each requiring the attempt's **newest** dispatch row to be the named one, with that exact activity id and an **in-process** (`dispatch`, never `operator_poll`) terminal observation that proves the outcome:
  - `revertProvisioningAfterDefinitiveFailure` → `verified` / `definitive_failure`: FAILED/REJECTED, no fingerprint mismatch, and an exact intent or (`fields_only` with a matching fingerprint). The retry policy is unchanged: a later dispatch is a new row.
  - `advanceProvisioningToTurnkeyCreated` → `turnkey_created`: COMPLETED, exact intent, no fingerprint mismatch, and observed result ids **equal** to the identity being written (compared only; the values written are the in-process response's).
  - A stale, mismatched, non-terminal, or operator-recorded observation enables neither. Existing L2/L3 smoke suites seed their `turnkey_created` fixtures by a direct, smoke-scoped SQL write instead.
- **Separate table** — `registration_provisioning_dispatches`, one row per dispatch, never overwritten (a retry after a definitive failure is a new row with a new sequence number).
  - **Immutable at insert:** id, credential id, sequence, evidence version, parent organization id, the stamping API **public** key, timestamp, `request_body`, `request_body_sha256`. No `UPDATE` names these columns.
  - **Write-once:** the activity id with Turnkey's fingerprint (verbatim), then the terminal group: status, who observed it (`dispatch` / `operator_poll`), Turnkey's `createdAt`, the observed sub-org / root user / wallet / address, the failure, and three verdicts.
  - **Mutable:** last observed status and time.
  - **Constraints:** unique `(credential_id, dispatch_seq)`, unique body digest, unique activity id (NULLs distinct), at most one dispatch per attempt without a terminal observation, digest format, and group-consistency CHECKs, every one explicitly named. A CHECK that the digest equals the database's own `sha256` of the body is included (built-ins only; `convert_to` is `STABLE`, which made Neon's acceptance an open question). It is **live-verified on Neon**: accepted at creation and enforced (a digest of other bytes, an uppercase spelling, and an empty body are refused; ASCII, escaped, and multi-byte bodies round-trip byte for byte with the database's digest equal to the application's). The application verifies the digest regardless.
  - **Fail-closed migration (M1).** One `DO` block, same convention as the S5 L2 block: `search_path` pinned to `pg_catalog, pg_temp` first; one `target_schema` constant (the scratch smoke swaps only it); the table created with `IF NOT EXISTS` and the relation under that name checked **immediately, before any further DDL** (re-audit M-1): an ordinary, permanent, non-partition table, neither an inheritance child nor a parent, with row-level security neither enabled nor forced and no policy, no user trigger or rule, and every column of a built-in base type and collation (no domain, enum, composite, or range) — so a same-named view, materialized view, foreign table, or hostile table is refused before the one-open index DDL ever runs. Then everything else is **proven** from the catalog. A reference copy of the same definition (all but the foreign key) is built in `pg_temp` in the same transaction, so the expected shape is what this server deparses for this text, never a hand-copied string. Checked: an ordinary, permanent, non-partitioned, non-inheriting table with no user trigger or rule and only validated constraints; every reference column (type, typmod, collation, NOT NULL, identity/generated, default); every reference constraint by name, kind, flags, key columns, and `pg_get_constraintdef`, with structurally identical backing indexes (including `NULLS [NOT] DISTINCT`); the foreign key structurally (exactly `credential_id → <target>.registration_attempts(credential_id)` through that table's unique index, NO ACTION, MATCH SIMPLE, not deferrable); the one-open index (on this table, btree, unique, valid, ready, immediate, not exclusion, exactly `(credential_id)`, no expression, the reference predicate); **no other index** on the table at all (only the reference constraints' backing indexes and the one-open index — Postgres adds none by itself, so an extra plain, expression, or predicate index is foreign); and no dependency of any constraint, default, or that index on anything but this table (plus, for the foreign key, `registration_attempts` and its index) — Postgres records none on built-ins, always one on a look-alike. Any mismatch RAISEs and rolls the block back; nothing is ever dropped, rebuilt, or repaired. Unrelated extra columns of a built-in base type are tolerated. **Live-verified** (see "Live verification"): the scratch-schema smoke (35/35) covers clean creation, an idempotent rerun, and refusal of every wrong object — a view, a materialized view, inheritance in either direction, RLS or a policy, an extra plain or expression index, an extra domain or enum column, a default calling a user function, and a hostile `search_path` with a look-alike `sha256`.
  - **The observed result ids are evidence, not identity.** The attempt's identity columns still come only from the in-process response. No pipeline code reads a dispatch row.
- **Two hashes, never conflated.** `request_body_sha256` is ours, over the bytes we sent. `turnkey_activity_fingerprint` is Turnkey's string.
  - A fingerprint of the form `sha256:<64 lowercase hex>` that equals our digest is a **match**; one that differs **fails closed to review**.
  - Any other form is stored and marked `unrecognized_form`. That alone decides nothing, so a format change at Turnkey cannot send every registration to review.
- **Intent** is compared structurally and key-order-insensitively, never as serialized strings: `exact`, `fields_only` (everything we sent is echoed unchanged, plus keys we did not send), or `mismatch`. A mismatch fails closed. **A `COMPLETED` create requires `exact`** (L2): `fields_only` is review even with a matching fingerprint, so a new server-echoed field can never silently become part of an activated account. A `FAILED`/`REJECTED` is definitive with an exact intent, or with `fields_only` only when the recognized fingerprint matches our body; an unrecognized fingerprint never makes `fields_only` definitive. The rule is one typed function (`classifyTerminalEvidence`), mirrored by the store CASes above.
- **A `COMPLETED` result** must name exactly one sub-org, one root user, one wallet, and one address; otherwise review.
- **Wallet-account binding (L3).** The follow-up `list_wallet_accounts` answer must contain **exactly one** account, and it must carry the created sub-organization as `organizationId`, the created `walletId`, the created address (same 20 bytes; hex case is not identity), `REAL_WALLET_ACCOUNT`'s curve, path format, path, and address format, and a non-empty `walletAccountId`. No "first match wins"; any disagreement is review. Not verifiable from this response: other wallets or private keys in the sub-organization (the lookup is per wallet) and the key material (`publicKey` is not compared).
- **An ambiguous `turnkey_created` write (L4).** If the evidence-bound advance throws or matches nothing, the attempt is re-read — never guessed. Still `provisioning_in_flight` with no identity: review, plus a fixed server-side marker (`[real-onboarding] turnkey_created_write_failed` / `_refused`). `turnkey_created` (or already `active`/`blocked`) with exactly the expected identity: the write committed and only its answer was lost, so the ordinary path continues. Anything else: a thrown `ProvisioningStateError` (`turnkey_created_state_contradiction`), a 500, never "pending". A failed re-read: thrown as `turnkey_created_reread_failed`. The markers are fixed strings — the project has no logging layer — and carry no identifier, body, attestation, stamp, or key.
- **Still review, by decision:** a completed create whose wallet-account read fails, or whose `turnkey_created` write genuinely did not happen. The evidence is kept; nothing resumes from it.
- **Bounded networking** (`lib/real/server/turnkey-provisioning.ts`; values **provisional**, no platform limit verified, no `maxDuration` set). Submit 10 s; one poll deadline of 8 s from the submit response; intervals 500 ms doubling to 2 s, never sleeping past the deadline; each read `min(3 s, time remaining)`; wallet-account read 5 s. The read count also has a hard ceiling. A timeout or abort is `unknown`.
- **Operator poller — record-only** (`lib/real/server/provisioning-activity-poller.ts`, run only through the env-gated `test/admin/poll-provisioning-activity.admin.test.ts`; dry run by default; a boundary test keeps it out of `runtime.ts`, routes, and the onboarding / registration / login modules).
  - It reads one activity by the id **already stored** on one dispatch row, in the stored organization, which must be the configured parent. The operator cannot supply an activity id.
  - It has no list, search, create, re-send, or mutation path, and its store type has no method that changes an attempt, account, passkey, or session.

- **Three identities, kept apart.** `app_user_id` is still the permanent application identity (sessions, foreign keys). The WebAuthn `user.id` (`real_passkeys.user_handle`) is still a random value **per credential** — a backup passkey has its own — and an existing credential's value is never rewritten. A *handle* is a third thing: a public label with **no authentication authority**. `auth.ts`, the session cookie, login, and every Turnkey request are unchanged and never read it.
- **Canonical handle.** Stored without `@`; lowercase ASCII; 3–20 characters of `a-z 0-9 _`; starts with a letter; no leading, trailing, or consecutive underscores (`^[a-z][a-z0-9]*(_[a-z0-9]+)*$`). `lib/real/handle.ts` is the one validator, used by the routes and the UI. Its order is fixed: trim ASCII whitespace, drop at most one leading `@`, **reject any non-ASCII code point before any case conversion**, lowercase, validate. No NFKC and no Unicode case folding, so nothing (Kelvin sign, dotted capital I, fullwidth Latin) can fold into ASCII.
- **ASCII look-alikes are accepted, not folded.** `pau1` and `paul` are different handles. The mitigation is presentational: wherever a handle will identify a payee it is shown beside the display name.
- **Registry: `real_account_handles`, one row per handle, forever.** `handle TEXT COLLATE "C" PRIMARY KEY`; `kind` is `reserved` or `claimed`; `app_user_id` is `UNIQUE` (one handle per account); `claimed_by_credential_id` records the passkey that authorized the claim. Because only the canonical lowercase form can be stored (a `CHECK` under `C` collation, plus `octet_length = char_length`), the primary key is case-insensitive uniqueness with no locale dependence. A `CHECK` ties `kind` to ownership (reserved: no owner; claimed: owner and claimer).
- **Immutable, never recycled — enforced by the database.** A row trigger refuses every `UPDATE` and `DELETE`, and a statement trigger refuses `TRUNCATE`. Both foreign keys (to `real_accounts`, and the composite `(app_user_id, claimed_by_credential_id)` to `real_passkeys` via the new `real_passkeys_app_user_credential_key`) are `NO ACTION`. The application has no update or delete operation for a handle. A typo is permanent; the UI's double entry and warning are the mitigation.
- **Reserved names are rows.** The migration seeds them as `reserved` with `ON CONFLICT (handle) DO NOTHING`, so the database refuses them even if the application list is bypassed. The list in code and the seed are kept identical by a test (minus `me`, which is too short to be stored at all).

### Handle Pay / Recipient Discovery — Slice A

**Status: COMPLETE/CLOSED.** A signed-in Real account can look up one exact `@handle` and learn whether it belongs to a payable account. This is **advisory discovery only: at this slice's closure users could not pay by handle** (Slice C has since built the Pay UI that calls it), and no payment path uses this lookup to route money. There is no schema change and no UI caller in this slice.

- **The route.** `POST /api/real/recipients/lookup`, body `{ handle }`. POST only — no search, prefix match, listing, or lookup by app user id or address. Order: the Real Mode flag (404 when off), then the session (401, and the handle store is not even built without one), then the body (400 for an unparseable or non-object body), then the resolver. Any failure after that is the generic 500. It sits behind the existing request gate (JSON-only, same-origin).
- **Canonicalization.** The handle goes through the one validator, `lib/real/handle.ts`. A malformed handle is a 400 carrying the validator's own reason, returned before any database read, so it reveals syntax only.
- **Resolution path: `handle -> app_user_id -> real_accounts.safe_address`.** One store read, `findPayableAccountByHandle` on the handle store: a single parameterized `SELECT` joining `real_account_handles` to `real_accounts` on `app_user_id`, restricted to `kind = 'claimed'`. It names exactly four columns (`handle`, `display_name`, `app_user_id`, `safe_address`) — no `SELECT *` — and the adapter maps the row field by field. **The Safe is the recipient account; the Turnkey owner address is never selected or used.** Static tests hold that for the Neon read, the in-memory twin, the resolver, and the route.
- **Server-only versus public.** `resolveHandleRecipient` (`lib/real/server/handle-recipient.ts`) returns the canonical handle, display name, `app_user_id`, and Safe address for server use. The route answers only through `toPublicRecipientLookup`, which builds its result from named fields, never a spread: `{ found: false }`, or `{ found: true, handle, displayName, isSelf }`. **`app_user_id` and `safe_address` never reach the browser.**
- **Self detection uses `app_user_id`** — the resolved account's against the session's — never an address and never anything from the request body.
- **One `not_found`.** A reserved handle, a nonexistent one, and a claimed handle whose account is currently unpayable all produce no row from the same single query and the same `200 { found: false }`.

See the residuals: this was never the payment-routing rule, and the lookup no longer applies it — it now requires a claimed handle and a valid Safe address only.
- **Read-only store surface.** The handle store gains exactly one method, a read. It still has no operation that updates, deletes, or recycles a handle; the exact-method test and the approved-handle-store-readers test were extended to name the new method and route, not loosened. `auth.ts` and `session.ts` still read no handle metadata.

The request body is `{ handle: <canonical> }` only. No Safe, `app_user_id`, owner address, or passkey/Turnkey data enters the state.

An answer applies only if both are current and the input still names the handle that was asked about. No `AbortController`.
- **Self.** When the account store already holds the user's own handle, the input is `self` immediately with no request — "That's your own @name." — and Review refuses. This is advisory UX; the server's `self_payment` (by `app_user_id`) stays authoritative. Direct-address self-pay is unchanged and left to the server.
- **Review.** Synchronous for an address or an already-found name; an unresolved name is looked up first, and review opens only after a current successful answer (and only if the amount was not edited meanwhile). The review row is "To": display name with `@handle` beneath, or `@handle` alone when there is no display name — never a display name alone. An address keeps the shortened address. No Safe, `app_user_id`, chain, gas, or wallet terms are shown.
- **Prepare.** Address: `{ recipient, amountBaseUnits }`, unchanged. Handle: `{ recipientHandle: <found.handle>, amountBaseUnits }` and nothing else. The lookup is never payment authority: the browser supplies no Safe, `app_user_id`, display name, or owner, and prepare re-resolves the handle on the server (Slice B), after which the attempt's own `recipient` and `callData` come from the server as before.

### Handle Pay Slice D — Durable Handle Identity in History and Restored Payments

**Status: HANDLE PAY SLICE D — COMPLETE / CLOSED.** Implemented; offline verification passed; an independent read-only audit passed; manual browser sanity passed — against the EXISTING confirmed Handle Pay, so **no new payment, no new Turnkey signature, and no database migration** were needed (the snapshot has been stored at prepare since Slice B). **Slice E (rate limiting / privacy hardening) is NOT STARTED**; mainnet readiness is later still. A payer now sees who a handle payment was to — the `@handle` and display name stored on the payment — on the approval, sending, and sent screens, after a reload, and in Recent activity, instead of an address. The slice is a mapper change plus client presentation: no change to `schema.sql`, `neon-store.ts`, `app/api/real/**`, `lib/real/payments/**`, `lib/real/signing/**`, Slice B's semantics, submit/reconcile/signing, Turnkey, Safe ownership, WebAuthn, or Practice Mode.

- **Public contract.** `recipientIdentity: { handle: string; displayName: string | null } | null`, nested, never flat. Handle payment: `handle` is the stored payment-time `recipient_handle` and `displayName` the stored `recipient_display_name` snapshot. Direct-address payment: always `null`. The existing `recipient` address stays on every public attempt and history entry for compatibility and as the fail-closed display fallback. **Never public:** `recipient_app_user_id` / `recipientAppUserId`, the owner address, Turnkey metadata, passkey metadata.
- **Snapshot semantics.** Historical identity is the payment's own stored snapshot. It is never joined from `real_account_handles` or `real_accounts` and never taken from the recipient's current profile, so an old payment's display name does not silently change when the recipient edits their profile. The immutable `@handle` is the durable anchor, and a history read needs no handle or account join. A payment made before Slice B, or by address, has no snapshot and is `null`.
- **Server mapping.** `toPublicRecipientIdentity` (`lib/real/server/payment-attempts.ts`, with the `PublicRecipientIdentity` type) is the explicit boundary from the server-side snapshot to public presentation data. Its parameter is `Pick<PaymentAttempt, "recipientHandle" | "recipientDisplayName">`, so it cannot read `recipientAppUserId`; it does no spread, no database read, and never infers an identity from `recipient`. The same helper feeds the existing explicit `toPublicAttempt` — so the identity appears on prepare success, submit, status by id, latest, and cancel (intentionally one mapper, not one per route) — and `toPaymentHistoryEntry`. No route file, query, or index changed.
- **Client source of truth.** Slice C's unpersisted `recipientLabel` (state, attempt-id matching, init/reset/cancel clearing) was removed entirely; no two competing post-prepare identity sources remain. **Before prepare** there is no attempt, so Review uses the advisory lookup. **After prepare** `attempt.recipientIdentity` — the server's stored snapshot — is authoritative for approval, sending, sent, reload (`init` → `latest` → attempt, with no lookup, no profile fetch, and no client persistence), and history. If the advisory name differed from the stored snapshot at prepare, the UI switches to the snapshot. A status check that replaces the attempt carries the identity from its own response. The identity is **read/presentation data only**: no mutation sends it back, and forged `recipientIdentity`, `displayName`, handle, or account fields in a request change neither the destination, the stored identity, nor signing/submit/reconcile.
- **Display rules.** One helper, `lib/real/display/payment-recipient.ts` (`describePaymentRecipient`), validates before anything is shown: `Smit Patel (@smit)`; `@smit` when the display name is null; the shortened `0x1234…abcd` for an address payment; a malformed identity falls back to the address and is never repaired or fabricated. Validation is fail-closed: an object with exactly the keys `handle` and `displayName`, a handle equal to its own canonical form (existing `canonicalizeHandle`), and a display name that is null or a non-blank string. A display name never appears without its handle.
- **Approval / resume UX (locked).** A restored Handle Pay approval shows `To: Name (@handle)` or `To: @handle` instead of the raw Safe address; the sending state shows `To Name (@handle)` and the sent state `$… to Name (@handle)`. "Only continue if you started this payment." is unchanged. A direct-address approval still shows the full address. No Safe or wallet terminology was added, and no recipient was added to the failed, unknown, or stranded states.
- **History.** Handle rows read `To Smit Patel (@smit)` or `To @smit`; address rows read `To 0x1234…abcd`. There is no reverse resolution: a direct-address payment to a Safe that belongs to a claimed handle remains an address payment. The identity is shown whatever the outcome (confirmed, failed, cancelled, pending, submitted, unknown) because it is who the payer intended to pay, not whether the transfer succeeded. A long name truncates while the `@handle` and the date do not shrink, and the full label is in the row's `title`. Amount, status, timestamps, transaction details, and the explorer link are unchanged.
- **Authorization unchanged.** By-id status and cancel stay payer-owned (another account gets `not_found`), latest is session-scoped, and history is session-scoped; no read-route authorization was weakened.
- **Static guards.** `payment-recipient-identity-schema.test.ts` holds `recipientIdentity` to exactly six files — the three server modules (`payment-attempts.ts`, `payments.ts`, `payment-history.ts`), the two stores, and the display helper (the components hand the whole attempt/entry to the helper and do not name it) — pins `toPublicRecipientIdentity`'s parameter type and its no-spread/no-read shape, and asserts neither public mapper names `recipientAppUserId` or the flat snapshot fields. Every existing restriction on `recipientAppUserId` / `recipient_app_user_id` and the snapshot names is preserved. The Slice B "no recipient identity public" assertions in `payments-history.test.ts` and `handle-pay-prepare.test.ts` were flipped deliberately to require exactly `{ handle, displayName }` and still no account id.
