## B. Hostname and relying-party decisions

- **[R]** Passkeys are created for one RP ID and signing goes browser → Turnkey directly using it; the server's origin checks never see that request (S5 M3). The RP ID must equal the exact host.
- **[D] B1 — the staging hostname.** One stable, dedicated hostname. **Proposed, not reserved and not approved:** a hosting project named `onchain-finance-staging` and the stable production hostname the platform assigns to it. **[P]** the platform assigns that hostname when the project exists, and it may differ from the project name (for example if the name is taken); nothing in this document predicts it. **A custom mainnet domain is not needed for the first Real-off staging deployment.** **[P]** whether a platform-assigned shared domain is acceptable as an RP ID is still unresearched, and so is whether renaming or deleting the project changes or frees its hostname; **[D]** decide both before any account is created, and treat the project name and hostname as permanent once a passkey exists.
- **[D] B1a — when the RP ID and origin are fixed.** For the Real-off AR-3 deployment **no RP or origin variable is needed** and none is set (Real Mode is off). The exact staging RP ID (the bare host) and exact HTTPS origin must be **established and recorded before any passkey enrollment**, i.e. before the first Real-on build (AR-8). AR-3 only records the hostnames the platform actually assigns (§P step 13); the decision is taken afterwards, with that evidence. Deployment-specific URLs and branch aliases are different hosts: they are never an RP ID and never listed as an origin.
- **[D] B2 — a single origin.** `NEXT_PUBLIC_REAL_ORIGIN` lists exactly one `https://<staging-host>` (no port). No preview, alias or localhost origin may be added. If a second origin is ever listed it widens who can reach the passkey and the request gate.
- **[D] B3 — permanence.** A passkey belongs to its RP ID. **[P]** what Turnkey does with a child organization's authenticators if the RP ID later changes is unverified; assume changing it strands every account registered under the old one. Staging and any later mainnet host must be **different** RP IDs so no passkey is shared across environments. Decide whether the staging host may ever become the pilot host before creating a single account.
- **[L]** Confirm the browser store receives the staging RP ID at build time (the `"localhost"` fallback above), and that registration on the staging host yields a passkey bound to it.

## C. Whole-deployment access protection

**Why this comes before any credential:** the app has **no caller authentication in front of registration**. The request gate checks `Origin`, `Sec-Fetch-Site`, `Referer` and `Content-Type`; it does not identify who is calling [R `request-gate.ts`]. Anyone who can reach the origin can start registration, bounded only by the 3C-1 global pool, which they can exhaust [R]. Registration creates real provider-side resources (Turnkey child organizations). Protection must therefore be at the platform layer and cover everything.

- **[R]** No hosting project exists: no `.vercel/` directory, no `vercel.json` [R].
- **[W] What the platform's public documentation says (§Q):** a 9 September 2026 changelog states that the platform's own login-based protection ("Vercel Authentication") can protect **all** deployments, **including production**, on every plan, without the earlier add-on.
- **[D] C1 — recommended mechanism: the platform's Vercel Authentication set to "All Deployments".** Password Protection is not required. **Do not enable** any of: shareable bypass links, deployment-protection exceptions, automation bypass secrets; and add no team member who does not need access. Each of those would open an unauthenticated path, which this runbook treats as a stop condition (§M). The operator confirms the setting on the created project; the documentation is not evidence that it is on.
- **[P] C2 — still to confirm from the live project, not from the changelog:** that "All Deployments" covers the production hostname, every per-deployment URL, previews and aliases on the operator's actual plan; whether direct requests to `/api/real/**` and static assets are covered; whether protection applies to deployments that already exist when it is switched on (it must be on **before** the first deployment can be reached, or the first deployment must hold nothing — §P); and who counts as an authorized viewer.
- **[D] C3 — the operator's plan and cost.** The control room's note is that the paid Pro plan is recommended for commercial product development and the free Hobby plan has personal / non-commercial restrictions; **the operator's actual plan is unconfirmed** and the choice, with its cost, is the operator's approval to give before AR-3 (§P step 1).
- **Coverage that must hold [L]:** from an unauthenticated client outside the operator's network, **each** of these is refused before reaching the app: the staging hostname; every `*.vercel.app`-style deployment URL for that project; every preview and branch alias; a direct `GET` and `POST` to `/api/real/session`, `/api/real/account/register/options` and `/api/real/account/login/options`; static assets. Record the status codes and any redirect target, and classify each result PASS / FAIL / NOT TESTABLE-UNDETERMINED under the attributable-denial rule in §P.5 (an application-level 404 is never a PASS).
- **[L]** The protection layer must not break WebAuthn or the request gate: confirm a passkey ceremony completes through it and that `Origin` and `Sec-Fetch-Site` reach the app unchanged.
- **[L]** Confirm the platform's CDN does **not** cache authenticated `/api/real/**` GET responses. The app sets no explicit `Cache-Control: no-store` on them and whether Next adds one is unverified [R ARCHITECTURE.md, S5 "Also noted"].

## D. Starting with Real Mode disabled and paid credentials detached

Order matters. Nothing paid or identity-bearing is attached until protection is proven.

1. **[D]** Create the hosting project with **only** `NEXT_PUBLIC_REAL_MODE_ENABLED=false` set **explicitly in every environment (Production, Preview, Development)**, and nothing else Real-related: **no** `TURNKEY_*`, `PIMLICO_API_KEY`, `DATABASE_URL`, `REAL_SESSION_SECRET`, RPC variable, RP or origin value. Preview deployments stay Real-off. **[R]** With the flag off the client is Practice-only and every `/api/real/**` route answers 404; the Turnkey, Pimlico and database code paths are not reached. (**[R]** an unset flag is also off, but AR-3 sets it explicitly so the intent is recorded.)
2. **[L]** Prove §C coverage on this credential-free deployment. Prove headers: `Content-Security-Policy: frame-ancestors 'none'`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` are present [R `next.config.ts`]. Record that there is **no** script CSP and **no** HSTS from the app [R].
3. Only after §C, §E and §K evidence and the approvals in §N, attach in this order, least costly and least authoritative first: the isolated database (§E–§G), the session secret, the RPC key, the Turnkey staging parent, and **last** the Pimlico key. Then turn the flag on through a rebuild and a **new** deployment, and give the Real-on build its own protected, recorded identity (§M).
4. **A flag-off deployment is not a project-wide off switch.** [W] A configuration change reaches only deployments created after it; **an earlier deployment keeps the configuration and credentials it was built and deployed with and can stay reachable and Real-on** until it is retired or made unreachable. Turning the flag off therefore protects only the deployments built after the change. Access protection, retiring old deployments, revoking credentials, pausing financial dispatch and already-running external operations are five different layers (§M); do not treat one as another. Keeping the number of Real-on deployments at one, and recording each by id, is what makes the rest of the ladder meaningful.
5. **[R]** Keep `NODE_ENV=production` for staging builds so the cookie is `Secure` and a missing database fails closed instead of silently using memory.

## G. Migration prerequisites

## M. Stop conditions and rollback

**Stop immediately and do not continue the step, when any of these is true:** any staging URL, alias or `/api/real/**` path is reachable without the protection; a bypass link, protection exception or automation bypass secret exists; a deployment exists that is not in the deployment inventory (below); **an unexpected deployment, promotion, alias change or queued or running build appears** (investigate; do **not** automatically redeploy, retire or delete anything, and do not delete evidence); a Git repository, deploy hook or integration is connected to the project without an authorizing grant; a secret appears in a log, response, repo file or chat; the connected database endpoint is not the new one; any block's digest does not match; the RPC reports a chain id other than 84532 or cannot serve `finalized`; an unexpected provider charge or a rising spend alert; more than one active payment or any duplicate payment; a payment state the app cannot explain; a Turnkey create whose outcome is uncertain; the flag, origin or RP ID in the build differs from the record; a chosen stop layer fails its rehearsal; the reviewer or operator is unavailable.

**Deployment inventory.** [D] From AR-3 onward the operator keeps a written list of **every** deployment the staging project has ever produced (identifier, creation time, commit, whether Real was on, its URLs and aliases, whether it has been retired). A new deployment never changes an older one's configuration (§A, §D step 4), so only this list says what could still be running with Real on. **[P]** how deployments are listed, retired, disabled or removed, and what an instant-rollback or alias change does to which deployment serves which hostname, are unverified and are checked at AR-3 against the live project.

**Preserve evidence before retiring anything.** Before any deployment is retired, disabled, removed or replaced — including as a rollback rung — preserve, in the evidence location, that deployment's **build log, runtime logs and request logs as the platform makes them available, its identifier, URL, creation time, source identity (commit and export manifest), variable names and environments, aliases, protection setting and members list at that moment**. Retiring a deployment may make its logs unavailable [P], so the capture comes first. Preserving evidence never includes copying a secret value. A step that would lose the only record of an incident waits for the capture or stops.

**The five layers — what each does and does not do.** They are separate; none implies another. The ladder below chooses among them.

| # | Layer | What it does | What it does **not** do |
|---|---|---|---|
| 1 | **Hosting access protection** (§C) | Controls who can reach a deployment URL. | Does not stop a reachable deployment's already-authenticated sessions from the operator's own browser, does not change its configuration or credentials, and does not retire it. [P] whether it applies to existing deployments when switched on. |
| 2 | **Retire old deployments** | Removes or disables a specific deployment so it stops serving. | Does not revoke the credentials it held; a flag-off **new** deployment does not do this to the old one. [P] mechanism unverified. |
| 3 | **Provider credential revocation** (Pimlico key, Turnkey API key, RPC key, Neon role / password, `REAL_SESSION_SECRET` rotation) | The only layer that stops **any** deployment, old or new, from using that provider; session-secret rotation signs everyone out. | Does not reverse anything already done. It also breaks every other user of the same credential, so credentials are never shared across environments. A removed hosting variable does **not** revoke the credential and does not affect old deployments. [P] revocation mechanics per provider. |
| 4 | **Durable financial dispatch pause** | Would stop new Prepare and Submit requests from every deployment at once. | **None exists.** This inspection found no durable, database-backed pause that the Pay routes consult; the Real Mode flag is deployment configuration, not shared durable state. Designing one is Tier A and an open decision (P-9). Until then do not describe the system as having a pause. |
| 5 | **Already-running external operations** | — | A UserOperation already sent, a Turnkey activity already dispatched or a database write already in flight **continues independently**. A signature already produced stays valid until its `validUntil` (up to 600 s) for whoever holds it (S5 L1). **Nothing in this runbook reverses a payment or cancels remote work.** Uncertain outcomes are investigated with authoritative evidence, never retried blindly. |

**Rollback ladder** (use the lowest rung that is enough; record each rung and the time):

1. **Contain reachability:** confirm layer 1 is on and that no bypass exists; if any Real-on deployment may be reachable by anyone else, treat the incident as ongoing.
2. **Stop new Real-on serving:** identify, from the deployment inventory, every deployment built with Real on; **preserve its evidence first (above)**, then retire each (layer 2). Deploying a new flag-off build is **additional**, not a substitute, because it does not alter the old ones.
3. **Stop provider use:** revoke the Pimlico staging key (stops sponsored sends), then the Turnkey staging API key (stops provisioning and reconcile reads), then the RPC key, at each provider (layer 3).
4. **Sign everyone out:** rotate `REAL_SESSION_SECRET` in a new deployment; this is effective only for deployments that carry the new value, so do it together with step 2 or 3.
5. **Detach the database:** rotate or revoke the staging database role at Neon [P]; removing `DATABASE_URL` from hosting configuration alone changes nothing for existing deployments.
6. **Tighten or remove** the hosting project's access, per the §C mechanism.

**What rollback cannot undo:** Turnkey child organizations already created; handles already claimed (immutable, never recycled); passkeys already registered; on-chain transactions; sponsored spend. The staging database is abandoned rather than cleaned — no deleting, truncating or "tidying" rows to hide an incident. An uncertain payment, provisioning dispatch, passkey forward or database write is investigated with authoritative evidence and an explicit operator procedure, never blindly retried.

### P.1 Decided safety requirement and the preferred mechanism

### P.5 Protection test outcomes (step 9)

Test from a client with **no** platform session (a private window with no sign-in, and a plain HTTP client from a network the operator does not use for the platform). Record each result as exactly one of:

- **PASS** — the response is **attributable to the platform's sign-in or denial layer** (a redirect to the platform's sign-in, or a platform-authored denial page or status, identifiable as the platform's and not the application's).
- **FAIL** — the request reached the application, or content from the application was returned.
- **NOT TESTABLE / UNDETERMINED** — the path cannot be exercised (for example, no preview or branch alias exists) or the answer cannot be attributed to a layer. **UNDETERMINED is not PASS.** A NOT TESTABLE row needs a written reason that the operator accepts; an UNDETERMINED row is treated as FAIL until resolved.

**An application-level "disabled route" answer — the app's `{"error":"Not found"}` with status 404, or the framework's own not-found page — comes from the application, not from the platform.** It proves the request **reached the app**, so it is a **FAIL for protection** on that path and never a PASS.

Paths to test, each **both** on the production hostname and on the deployment-specific URL: (a) `/`; (b) `GET /api/real/session`; (c) `POST /api/real/account/register/options` and `POST /api/real/account/login/options`; (d) **a generated `/_next/static/` asset** — its exact path comes from the deployed page (read it in the operator's authorized browser session; record the exact path used); (e) **an existing `public/` asset, if present** — **[R]** at HEAD `3a5708a` the `public/` directory contains no tracked file, so there is none to test; record that, and optionally also test the framework-served `/favicon.ico` (from `app/favicon.ico`); (f) any alias or preview URL that exists — with the preferred no-Git mechanism none is expected, so record "none exists" as a NOT TESTABLE row with that reason.

**What AR-3 leaves undone, by design:** the RP ID and origin decision; every credential; the database; Turnkey, Pimlico and RPC; the schema rehearsal; Real-on; any registration, passkey, balance, payment or funding. Each needs its own request (§N). **Any flag-on deployment created later is a new deployment and does not change this one; keep the inventory.**
